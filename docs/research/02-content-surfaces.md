# BelloCode content surfaces: implementation research

Research snapshot: 16 November 2026. Target: macOS 15+, Swift 6.x, Apple Silicon. Estimates are relative engineering sizes for a first production-quality implementation (S: days, M: 1–3 weeks, L: 3–8 weeks, XL: 2+ months); integration, accessibility, and regression work can change them. They are judgments, not benchmarks. No claim here establishes 120 Hz on BelloCode hardware: a 120 Hz display affords **8.33 ms for the entire frame**, not 8.33 ms for each component. Measure release builds on both 60 Hz and 120 Hz Macs, with Instruments' SwiftUI, Time Profiler, Core Animation and allocations tools. Include real streaming, input, image decoding, find and trackpad momentum; report frame-time percentiles, dropped frames, peak/resident memory and first-use latency. Apple's [animation hitch guidance](https://developer.apple.com/documentation/xcode/understanding-hitches-in-your-app) and [TextKit 2 session](https://developer.apple.com/videos/play/wwdc2021/10061/) describe relevant measurement/layout concepts.

## 1. Streaming transcript

**Recommendation: a single selectable AppKit TextKit 2 document (`NSTextView` in `NSScrollView`) with block-level rich text and carefully bounded attachments, backed by a canonical transcript model; spike before committing. Size: XL.** This puts selection and copy across message boundaries into one native selection domain, the strongest differentiator in the requirements. Keep controls sparse: render ordinary text, headings, code, links and simple chips in the text system; use view-backed attachments or positioned overlays only for interactive tool/diff controls, instantiated near the viewport. Tables require a separately tested layout strategy, not an assumption that SwiftUI tables embed cheaply. Store a mapping from message/block IDs and model offsets to document ranges and attachment IDs. Use a separate native accessibility representation for controls and verify VoiceOver selection, actions, keyboard and focus. `NSTextView` does not automatically solve all of these interactions, and giant attachments, native table layout and frequent text-storage edits could defeat viewport layout. If the spike fails, use a virtualized AppKit row view with a deliberately implemented cross-row selection model; if native selection proves impractical, make a product decision on an embedded web transcript rather than silently losing the requirement.

| Architecture | Strength | Cost / constraint |
|---|---|---|
| SwiftUI `LazyVStack` / `List` | Fastest prototype, idiomatic cards; lazy realization | Separate `Text`/view selections do not automatically form one cross-message selection; variable height and identity changes can shift offsets. List behavior and virtualization differ; measure, don't assume. |
| `NSTableView` / `NSCollectionView`, self-sizing reusable cells | Mature native reusable rows and interactive cards; updates can target tail | Cross-cell drag selection, copying and find across offscreen rows require a model, hit-testing and custom drawing; dynamic heights require explicit anchor compensation. A single huge message still needs its own virtualization. |
| One TextKit 2 `NSTextView` plus attachments | One native selection/find domain; TextKit 2 provides viewport-oriented layout, attributed text and native input/accessibility | Rich interactive widgets, tables, viewport attachment lifecycle, memory and layout invalidation are hard; TextKit 2 is not a guaranteed 120 Hz or zero-bug solution. [STTextView's issue list](https://github.com/krzyzanowskim/STTextView#-textkit-2-bug-reports-list) demonstrates reported problems, not necessarily current macOS 15 behavior. |
| Custom `CALayer` layout | Control over viewport and frame budgets | Must implement shaping, bidirectional text, accessibility, selection, copy, focus and hit testing; disproportionate risk. |
| `WKWebView` transcript | DOM ranges/select across messages, mature HTML/CSS tables, web tooling | Virtualization and cross-virtualized selection still conflict; DOM mutation/layout, JS bridge, accessibility and process memory add cost; native widgets and exact scroll anchors still need work. |

**Streaming plan.** Keep immutable completed messages and a versioned mutable tail. Append network chunks to a buffer; coalesce updates at a measured cadence, e.g. at most once per display frame, and parse off-main on a serial worker. Apply only the changed range on the main actor, discard stale results by message/version, and avoid replacing the entire attributed document or rebuilding all view bodies. For very long tails, rate-limit and parse only safe regions where correctness is demonstrated; never assume a blank line always closes a block: lists, block quotes, reference definitions, setext headings and tables can change interpretation later. On completion, parse the full message canonically and reconcile. Put explicit limits on oversized code fences, image dimensions and attachment count; compute highlighting and image decoding away from the main thread, then apply versioned results. Cache layout by stable block ID, width, font, theme and content version; invalidate only affected entries.

**Anchoring and selection.** Before an edit record whether the viewport is within a small bottom tolerance and whether the user is actively scrolling. If following, keep bottom aligned after layout; scrolling upward cancels follow until user explicitly returns to the bottom or presses a jump-to-latest control. Otherwise capture a stable visible message/block ID, text position and pixel displacement; after layout restore the same position and displacement, including for image load, expansion, resize and updates above it. Avoid overriding an active drag or momentum; preserve selection as model positions across updates, including the streamed tail. Search the canonical model off-main, index normalized plain text with offset mapping, reveal unloaded matches and highlight without disrupting selection. Define copy of chips, collapsed content, tables and diffs explicitly; clipboard plain text and rich formats should be consistent. Check RTL, emoji, grapheme boundaries and UTF-16/UTF-8 conversion.

| Markdown option | Evidence and streaming implication |
|---|---|
| [`swift-markdown`](https://github.com/swiftlang/swift-markdown) / cmark-gfm | Recommended canonical parser: GFM-powered immutable tree; value-tree structural sharing is **not** evidence of incremental parsing of appended source. Reparse tail or validated window. |
| [Down](https://github.com/iwasrobbed/Down) | cmark wrapper, attributed/HTML output; upstream last pushed 2023-07-15; older cmark, so verify dialect and maintenance. Its cited 127 ms *War and Peace* figure is upstream's old cmark benchmark, not a UI or streaming measurement. |
| [MarkdownUI](https://github.com/gonzalezreal/swift-markdown-ui) / [Textual](https://github.com/gonzalezreal/textual) | SwiftUI renderers; MarkdownUI explicitly maintenance mode, Textual successor. Attractive for isolated content; neither establishes cross-message selection or incrementality for this architecture. |
| Custom incremental parser | Can minimize work but CommonMark/GFM lookbehind and forward references complicate exactness. Do not write one first; use only after profiling and differential tests against canonical GFM. |

Incomplete input is provisional: unclosed fences are valid-to-EOF under CommonMark; show the code as it arrives. Do not synthesize closing delimiters into the stored source. For ambiguous emphasis/link/table constructs show the canonical parse of the current prefix, accepting limited local restyling as more characters arrive; never freeze an allegedly finalized block if a later reference definition can change it. Test every split point of a corpus against final full parsing and ensure no lost text, broken selection or large jumps. See [CommonMark spec](https://spec.commonmark.org/current/) and [GFM tables](https://github.github.com/gfm/#tables-extension-).

**Risks:** attachment interaction and table fidelity; TextKit 2 regressions/fallback to TextKit 1 when incompatible APIs are used; giant-document layout/memory; selection crossing view attachments; accessibility; changing markup semantics. TextKit 2 viewport layout is documented, but whether this workload reaches the target is unverified. **Spike to de-risk:** build 10,000 mixed messages with 10 MB total text, 100 cards, GFM tables, async images and one 100 KB streaming fence; test drag/copy across 20 messages, find an offscreen match, expand above the viewport during momentum and follow/release/rejoin. Record p50/p95/p99 frame times, allocations and input latency in release on an identified 120 Hz machine. Compare against the cell fallback with identical data and interaction; agree a frame-drop budget before production.

**Existing implementations:** [Exyte Chat](https://github.com/exyte/Chat) ships a SwiftUI customizable message-cell framework and media composer; it is evidence of a cell-based implementation, not proof of 10,000-message performance or cross-cell selection. [Copilot for Xcode](https://github.com/Intitni/CopilotForXcode) is an open-source native macOS AI coding assistant; its repo provides a concrete application to inspect, but its performance and transcript selection guarantees have not been established here. Neither should be taken as a benchmark.

## 2. Syntax highlighting

**Recommendation: SwiftTreeSitter with selected tree-sitter grammars and queries, optionally Neon for range invalidation; share a highlighting service between code views and transcript fences. Size: L.** Tree-sitter supports incremental tree edits and reparsing; [SwiftTreeSitter](https://github.com/ChimeHQ/SwiftTreeSitter) exposes queries, nested language layers and language mapping. Maintain one parser/tree per actively edited document or streaming fence; apply edits with correctly translated byte offsets and points, query affected/visible ranges, run parsing off-main, and publish versioned token spans. Cache completed blocks by language, content hash and grammar/query version; theme via token-to-color mapping, invalidating colors separately from parsing. Unknown languages and excessive files fall back to plain monospaced text. Account for grammar licenses, embedded language injections and large single lines.

| Option | Cost, coverage and maintenance |
|---|---|
| [SwiftTreeSitter](https://github.com/ChimeHQ/SwiftTreeSitter) + [Neon](https://github.com/ChimeHQ/Neon) | Incremental parses and query-driven themes; per-grammar/query packaging, native binaries and offset management. Neon is optional, not a text view. Its README explicitly describes unresolved TextKit 2 on-keypress flicker integration; validate on target OS. |
| [Highlightr](https://github.com/raspu/Highlightr) / highlight.js via JavaScriptCore | Upstream advertises 185 languages and 89 styles; convenient broad static coverage, but whole-string highlighting and JS bridge/attributed-string costs must be measured. No incremental parse guarantee. Highlightr declares itself unmaintained in 2026. |
| [Splash](https://github.com/JohnSundell/Splash) | Lightweight Swift-language-specific highlighter and configurable output; insufficient language coverage for a coding agent; no established incremental editor support. |
| Custom lexer | Small for a fixed subset; many grammars, nested languages and theme semantics become ongoing work. |

**Risks:** query/grammar mismatch, Swift 6 concurrency and ABI compatibility, invalid byte/UTF-16 ranges, parse cost for large or adversarial inputs. **Spike:** compare cold/warm parse, peak memory and p95 edit-to-colored-visible-text latency for 10 KB and 1 MB Swift, TypeScript and embedded HTML/JS; stream 1–16 character chunks, alter the first line and theme; include Unicode and incomplete code. Compare with plain text and Highlightr. No independent cost measurements were found for this exact setup.

## 3. Composer

**Recommendation: `NSTextView` wrapped with `NSViewRepresentable`, with a constrained auto-growing scroll view and an external attachment model. Size: L.** NSTextView supplies native text input, services, selection and undo. Measure intrinsic/used text height at width, cap to a sensible fraction of the window, then scroll internally; coalesce measurement after text/layout changes and avoid resetting text/selection on every SwiftUI update. Integrate completion UI via a popover anchored to the insertion rect; model mention tokens as stable text ranges/attributes and attachments as separate chips with accessible remove buttons. Insert as one undoable operation. Pasted files/images must preserve normal text paste and be stored independently of attributed text. For IME, do not replace marked text, intercept candidate navigation or submit on Return while composition is active; use `NSTextInputClient` marked-text semantics. Slash and @ completion must respect selection and caret moves. History on Up/Down only at the proper boundary with no marked text, completion, or multiline navigation; preserve the draft.

| Option | Assessment |
|---|---|
| AppKit `NSTextView` | Native input/undo/paste and control of selection, key events, text storage and completion; representable synchronization and layout management require care. |
| SwiftUI `TextEditor` | Simple binding and styling; for rich token ranges, paste routing, marked text and anchored completion may require AppKit bridging anyway. Feature behavior must be tested on macOS 15. |
| Custom input view | Maximum control, but recreates IME, accessibility, undo and system editing behaviors; avoid. |

Sources: [NSTextView](https://developer.apple.com/documentation/appkit/nstextview), [NSTextInputClient](https://developer.apple.com/documentation/appkit/nstextinputclient), [NSViewRepresentable](https://developer.apple.com/documentation/swiftui/nsviewrepresentable). **Risks:** IME corruption, selection loops in SwiftUI bridging, undo grouping, pasting large/remote images, privacy and accessibility. **Spike:** grow and shrink input while exercising Japanese and Chinese IMEs, emoji, paste image plus text, undo/redo mention insertion, completion cancellation, multiline history and VoiceOver. Verify that Enter during composition never submits.

## 4. Diff and file viewer

**Recommendation: prototype CodeEditSourceEditor for the single-file viewer and build a separate virtualized, line-oriented diff view with shared line metrics and highlighter. Size: XL.** This is one implementation strategy: use the editor for document interaction, not two whole text editors as an assumed split-diff solution. Model rows as paired old/new lines with placeholders, stable hunk/line IDs and a single vertical coordinate system; unified mode uses the same row model. Shape only viewport + overscan, cache line heights by width/font/content version, and synchronize horizontal scrolling where appropriate. Compute line diff off-main; compute intra-line spans only for changed visible/near-visible pairs and bound expensive comparisons, with a plain line-level fallback. Map Unicode ranges correctly. Preserve side, line and character positions for selection, copy and find. Hunk accept/reject operates on a versioned base and checks context/current file content before applying; a stale hunk must refresh or fail explicitly, not silently patch the wrong lines. Add native accessible controls and keyboard navigation.

| Option | Assessment |
|---|---|
| [CodeEditSourceEditor](https://github.com/CodeEditApp/CodeEditSourceEditor) / [CodeEditTextView](https://github.com/CodeEditApp/CodeEditTextView) | Shipped CodeEdit-oriented code editor, tree-sitter, find, line numbers and diff-related features; evaluate APIs and large-file behavior. Lower-level view explicitly disclaims RTL and full NSTextView parity. Its diff support does **not** prove it provides split virtualized hunk actions. |
| [STTextView](https://github.com/krzyzanowskim/STTextView) | TextKit 2-based NSTextView replacement with plugins and listed TextKit bug reports; good comparative spike, not proof every listed issue persists on macOS 15. |
| [Runestone](https://github.com/simonbs/Runestone) | Real iOS implementation using tree-sitter and a line tree; useful architecture reference, not a drop-in macOS component. |
| Custom TextKit 2 | Native text selection, but split line alignment, scalable attachment and hunk UI remain significant engineering and OS risk. |
| Custom line layout | Best control over large diff virtualization and paired rows; must implement selection, shaping, accessibility and input accurately. |

**Risks:** bidi shaping, proportional/wrapped line alignment, million-line file memory, huge lines, selective patch correctness and accessibility. Set limits and expose a graceful large-file mode; don't claim arbitrary-size support. **Spike:** open a 100,000-line file and 10,000-line changed diff with long Unicode lines, resizing and split/unified toggle; test cross-hunk selection, synchronized scroll, word spans, accept/reject after a concurrent edit, and memory and p95 frame time. Compare CodeEdit and STTextView for file-viewer requirements before pinning a dependency.

## 5. Embedded terminal

**Recommendation: SwiftTerm `LocalProcessTerminalView` on macOS, behind a terminal abstraction; size L.** Its [README](https://github.com/migueldeicaza/SwiftTerm) documents AppKit, PTY/local process support, selection, find, Unicode and optional Metal rendering. Use its existing PTY/process integration where suitable; otherwise manage shell spawn, environment, working directory, window-size propagation/SIGWINCH, lifecycle and cleanup explicitly. Test shell login semantics, process exit, resize, scrollback memory, mouse reporting, alternate screen, true color, clipboard/OSC policy and IME. Do not perform process I/O on the main actor. Treat terminal output as untrusted and define clipboard, hyperlinks and escape-sequence policies.

| Option | Assessment |
|---|---|
| [SwiftTerm](https://github.com/migueldeicaza/SwiftTerm) | MIT, Swift/AppKit embeddable terminal and optional Metal; convenient integration and app-owned process model. Profile chosen renderer and verify compatibility with actual TUIs. |
| [libghostty](https://github.com/ghostty-org/ghostty) | MIT Ghostty project; native Metal/CoreText renderer and real embedded examples. Upstream says libghostty-vt API signatures are still in flux; distinguish VT parsing/state from complete terminal embedding. Swift/Zig/C build, packaging and API churn increase integration cost. |
| [xterm.js](https://github.com/xtermjs/xterm.js) in WKWebView | Mature web terminal, but process bridge, IME, native accessibility and WebKit/JS process overhead require integration; xterm.js itself is not a PTY. |
| Build terminal | Escape protocols, Unicode, rendering and PTY edge cases make this a large ongoing project. |

Ghostty upstream describes performance in broad comparative terms, including an approximately 100× claim for particular benchmark classes; it is a vendor claim, not a BelloCode measurement or universal latency figure. See [Ghostty architecture/benchmark claims](https://github.com/ghostty-org/ghostty#competitive-performance) and [libghostty embedding examples](https://github.com/ghostty-org/ghostling). **Risks:** renderer/terminal protocol gaps, scrollback cost, process lifecycle, Swift 6 integration. **Spike:** run `vim`, `tmux`, a color/Unicode torture corpus and rapid output in both SwiftTerm renderers; measure CPU, frame times, latency, memory and resize correctness, then compare a pinned libghostty embedding if the result misses agreed targets.

## 6. Embedded browser pane

**Recommendation: use an app-owned `WKWebView` per tab for a lightweight pane, but gate the agent automation promise on a same-instance automation spike; use CEF instead if existing CDP tooling is a hard requirement. Size: XL including automation, M–L for basic browser UI.** A separate browser is not equivalent to controlling the visible pane. Define an explicit versioned local automation bridge to the app, with tab IDs, navigation lifecycle, request correlation, cancellation, timeouts and authorization. WK navigation/delegate APIs plus `callAsyncJavaScript`/`evaluateJavaScript`, user scripts and message handlers can implement DOM inspection, scripted actions, element picking and console wrappers for reachable contexts; capture screenshots with `takeSnapshot`. This is an app-specific protocol, not CDP/WebDriver and not full fidelity: injected JS cannot generally observe all network activity, cross-origin frame internals, native dialogs or service-worker activity. JS is page-controlled and can be tampered with; isolate worlds where possible, validate messages, avoid exposing app privileges to arbitrary sites and treat automation results as untrusted. Avoid inventing production network interception around private APIs.

| Option | Same visible browser / capabilities | Cost and limits |
|---|---|---|
| WKWebView | `WKWebView` per tab; native navigation, JS bridges, screenshot, data stores and opt-in Web Inspector. [WebKit inspection](https://webkit.org/blog/13936/enabling-the-inspection-of-web-content-in-apps/) uses `isInspectable`, Safari Develop menu; availability depends on OS/settings and is not a CDP endpoint. | Public APIs do not expose a general Chrome DevTools Protocol server. Safari WebDriver controls Safari, not a documented arbitrary embedded WKWebView; Playwright's bundled WebKit is not attachment to this instance. Out-of-process control requires app-owned IPC + supported APIs/injected JS; generic WebDriver/CDP compatibility is unverified and must not be promised. |
| CEF embedded Chromium | CEF provides embedded Chromium and remote debugging; a CDP-capable client can potentially operate the same tab. Verify target discovery, browser version, process model, sandbox and security in a real build. | Large distribution/download and process footprint; frequent Chromium/security upgrades, packaging/signing/notarization, native integration and licensing obligations. Do not assert a fixed size or exact Playwright support without measuring pinned builds. |
| External Chrome | Mature Chrome/CDP ecosystem and user-visible window when launched with debugging enabled. | Separate application/window rather than a truly embedded pane; profiles, lifecycle and remote debugging ports require careful isolation. An existing user's Chrome is not automatically controllable; recent Chrome has [remote-debugging profile restrictions](https://developer.chrome.com/blog/remote-debugging-port). |

**Capability details:** share a `WKWebsiteDataStore` intentionally for tabs in one profile; use distinct persistent stores via the [identifier API](https://developer.apple.com/documentation/webkit/wkwebsitedatastore) where supported or nonpersistent stores for private sessions. Verify true cookie/storage isolation and migration on macOS 15; process pools are not a substitute for storage boundaries. Downloads, file upload, permissions, popups and authentication need delegates/UI. [WKWebView snapshot](https://developer.apple.com/documentation/webkit/wkwebview/takesnapshot(with:completionhandler:)) provides a web-view image, not a promise of full-page or browser-chrome capture. Element picker can use injected hit testing and overlay, with cross-origin frames and shadow DOM limitations. Public `WKNavigationDelegate` gives navigation events, not a full DevTools network log; app JS instrumentation misses cached, worker, early and native requests. A custom URL scheme handler is for schemes the app handles, not a general HTTP(S) interceptor. Full-fidelity network/console capture is **unverified/unavailable through a documented general-purpose WKWebView public API**; Inspector is user-facing tooling, not a supported automation API. Relevant APIs: [WKWebView](https://developer.apple.com/documentation/webkit/wkwebview), [WKContentWorld](https://developer.apple.com/documentation/webkit/wkcontentworld), [Safari WebDriver](https://developer.apple.com/documentation/webkit/testing-with-webdriver-in-safari), [Playwright browser management](https://playwright.dev/docs/browsers), [CEF](https://github.com/chromiumembedded/cef).

**Risks:** automation plugin may require CDP features WK cannot supply, cross-origin pages, in-page adversarial scripts, tool/visible-state divergence, browser-security updates with CEF. **Spike:** connect the actual agent plugin to the exact user-visible tab; navigate, click, type, inspect DOM, screenshot, handle a popup, cross-origin iframe and authenticated cookie, and capture console/network. Test a second profile and external client process. Document which operations are impossible using public APIs; if the plugin needs unmodified CDP/network events, benchmark a signed/notarized CEF prototype and make the engine choice before production.

## 7. Animations and micro-interactions

**Recommendation: SwiftUI for low-frequency state transitions and AppKit/Core Animation for scroll-coupled or layer-backed details; disable implicit animation for streaming/layout updates. Size M across surfaces.** Animate disclosure, hover, copy confirmation and jump-to-latest affordances with short interruptible transitions; respect Reduce Motion and keyboard/VoiceOver state. Keep stream text updates, measured heights and scroll-anchor corrections out of animation transactions (`Transaction(animation: nil)` / appropriate AppKit `NSAnimationContext` and `CATransaction.setDisableActions(true)`), while leaving deliberate user actions animated. Don't animate every token, shadow, layout constraint or giant text layer. Cache/prepare content off-main, avoid synchronous image decode, coalesce invalidations, and avoid nested animation state that fights tracking. Core Animation compositing is not free: offscreen rendering, blending and large layer trees can hitch.

| Option | Assessment |
|---|---|
| SwiftUI animation | Declarative and convenient for bounded state changes; changing layout across a large transcript can invalidate too much. |
| Core Animation / AppKit | Explicit transactions, interruptible layer properties, control over implicit actions; layer count, compositing and main-thread updates still matter. |
| Per-token animated views | Visually noisy, many invalidations and layout churn; avoid for streaming. |

Sources: [Core Animation transactions](https://developer.apple.com/documentation/quartzcore/catransaction), [SwiftUI transactions](https://developer.apple.com/documentation/swiftui/transaction), [Reduce Motion](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion). **Risks:** anchor and selection move during animations, dropped frames, motion sensitivity. **Spike:** profile repeated expand/collapse and image arrival while scrolling and streaming at 120 Hz, with Reduce Motion both enabled and disabled; inspect frame-time spikes and check anchor/selection fidelity.

## Consolidated recommended third-party Swift dependencies

The upstream activity dates below are repository `pushed_at` observations on 16 November 2026, not guarantees of maintainer availability, release quality or Swift 6 strict-concurrency compatibility. Pin reviewed releases/commits; audit all transitive components, grammars, queries and bundled license notices before shipping. Licenses are upstream-reported where identified; verify the exact pinned version and bundled code.

| [SwiftTreeSitter](https://github.com/ChimeHQ/SwiftTreeSitter) | BSD-3-Clause | Pushed 2026-08-12; incremental parser binding. Tree-sitter core is MIT; each language grammar/query has its own license and compatibility requirements. |
