# Dev Containers, dual environments and Chrome

Research, 2026-11-18. Scope: host opencode and host file editing, container execution, Rancher Desktop dockerd; no project code runs on the host. This is a proposed compatibility subset, not a claim that it is implemented. The current architecture and its actual guarantees are in [containers](../features/containers.md), [Git](../features/diff-git.md), [browser](../features/browser.md), [browser spike](../spikes/G3-browser-bridge.md), [opencode research §6](05-opencode-integration.md) and [Rancher research](06-containers-rancher.md). The older Rancher recommendation to containerize opencode was superseded by the owner's decision in [plan §0](../PLAN.md). No separate git-parity note was found.

## 1. Dev Container specification and BelloCode mapping

The [specification](https://containers.dev/implementors/spec/), [metadata reference](https://containers.dev/implementors/json_reference/) and [JSON schema](https://github.com/devcontainers/spec/tree/main/schemas) define configuration and lifecycle semantics; the [reference CLI](https://github.com/devcontainers/cli/tree/main/src/spec-node) is an implementation, not a required dependency. Config can also come from image/Feature metadata, with defined merge rules; supporting JSON fields alone is not full conformance. Discover the documented `.devcontainer/devcontainer.json` and `.devcontainer.json` forms, and explicitly resolve supported named configurations. Parse JSON with comments, validate types, resolve supported variables and paths, and display errors with source locations. Never silently ignore a meaningful unsupported field or image metadata.

| Property | Meaning and proposed mapping |
| --- | --- |
| `image` | Pull/create the workspace from the selected image under existing image policy. Record resolved digest and architecture. |
| `build.dockerfile`, `build.context`, `build.args`, `build.target` | Resolve paths relative to the config per spec; send a bounded, `.dockerignore`-filtered build context and options to the Engine build API. Validate context symlinks, base-image policy, args and target; no secret build args. Dockerfile `RUN` is project code inside the builder, not on the Mac. See [Engine build API](https://docs.docker.com/reference/api/engine/version/v1.47/#tag/Image/operation/ImageBuild). BuildKit features and base-image policy enforcement need independent verification. |
| `dockerComposeFile`, `service`, `runServices` | Files compose into one model, `service` selects the workspace and `runServices` the startup set. This is **not** equivalent to today's service-only Compose subset: merge, interpolation, dependencies, build, networks, volumes, commands and the workspace service must be validated together. Initially refuse Compose dev-container configurations; add a separately specified, tested subset later, with exact unsupported keys and locations. Never pretend a partial stack started. |
| `workspaceFolder`, `workspaceMount` | `workspaceFolder` is the in-container working directory; `workspaceMount` specifies its mount. First support only validated bind mounts that preserve the existing identical absolute host/container path, including required worktrees and Git common directory. A different requested path is refused until a complete bidirectional path mapper exists; do not silently replace it. |
| `mounts` | Support policy-checked named volumes and explicitly approved read-only host binds under allowed roots; workspace writes remain explicit. Refuse socket, device, broad home/root and unapproved host binds; show source, target and mode. Validate canonical paths and mount overlaps. |
| `containerEnv` / `remoteEnv` | Container environment applies at container creation; remote environment applies to tool/editor and lifecycle exec processes, not all container processes. Apply `remoteEnv` to helper exec and lifecycle processes, never the host opencode process. Restrict substitutions and surface unresolved values; do not copy the host environment wholesale. Values are not secret storage. |
| `containerUser`, `remoteUser`, `updateRemoteUserUID` | Container user controls the container default; remote user controls spawned development processes. Resolve and inspect both, run lifecycle commands as remote user, and test actual mount ownership. UID updating is a Linux-host-oriented spec behavior, not a promise that macOS numeric IDs map through Rancher sharing. Reject a requested UID rewrite until safely supported; never assume root is needed. See [VS Code non-root guidance](https://code.visualstudio.com/remote/advancedcontainers/add-nonroot-user). |
| `forwardPorts`, `portsAttributes` | Map supported integer ports, labels and HTTP/HTTPS to the existing on-demand Mac-loopback relay. Report chosen local port and remote target. Refuse unsupported host:port targets and attributes whose behavior cannot be honored, including required fixed-port conflicts; do not elevate or publish to the LAN. Automatic opening and notification are preferences subject to policy. |
| `initializeCommand` | Runs on the **host**, before container creation, and can be shell, argv or parallel object. Never execute it; visibly block the configuration and explain why. An approved human may replace it with a container-safe setup step or perform an independently approved host operation; silently moving it changes semantics. |
| `postCreateCommand`, `postStartCommand`, `postAttachCommand` | Execute inside the workspace as remote user, in spec order and correct lifecycle frequency, after explicit review of repository-controlled commands. Preserve shell-string vs argv vs parallel-object semantics, output, failure and cancellation. Define BelloCode attach as a user session attachment, not every agent tool call. Unsupported `onCreateCommand`, `updateContentCommand`, `waitFor` and other lifecycle variants must block until implemented; do not skip setup. |
| `features` | OCI-distributed packages contain `devcontainer-feature.json`, `install.sh` and optional files; the installer normally runs as root **during image build**. Metadata can add lifecycle commands, environment, privileges and dependencies. Resolve and pin digest, verify policy, dependency order, options and metadata, fetch via registry API, then stage into a controlled derived-image build. Native Swift orchestration is possible in principle, but secure extraction, registry auth, reproducibility and spec parity require a spike; initially refuse Features rather than silently omit. [Feature spec](https://containers.dev/implementors/features/); [CLI implementation](https://github.com/devcontainers/cli/blob/main/src/spec-node/containerFeatures.ts). |
| `customizations` | Tool-specific, e.g. VS Code extensions/settings; never run or install them on the Mac. Show namespace and ignored settings, with explicit acknowledgement that editor-specific customization is not applied. Reject a customization if policy cannot assess its execution effects. |
| `hostRequirements` | Validate CPU, RAM, disk and GPU against available VM capacity where measurable; show unknown separately from satisfied. Do not claim GPU support. Insufficient required resources block; optional GPU does not. |
| `runArgs`, `privileged`, `capAdd`, `securityOpt` | Refuse arbitrary `runArgs`, privileged mode, added capabilities, weakened security options, host namespaces/devices and Docker sockets. A future narrowly allowlisted exception requires enterprise policy and explicit review; acceptance is never inferred from a checked-in config. |
| `shutdownAction` | `stopContainer` maps to owned container stop; `none` leaves it running. Reconcile with idle-stop and app-close policy explicitly, show effective behavior, and refuse conflicting settings rather than falsely claiming exact spec behavior. Compose `stopCompose` awaits Compose support. |

**Native feasibility:** Swift can resolve the supported JSON, query registries and make Engine API pull/build/create/start/exec/inspect/stop calls without a host Node, Docker CLI or devcontainer CLI. The Engine provides primitives, not spec interpretation, lifecycle scheduling, Feature security, Compose translation or policy enforcement. Variable interpolation, `devcontainer.metadata` image labels and Feature metadata merge, image `ENTRYPOINT`/`CMD`, lifecycle ordering, UID mapping, build secrets and `.dockerignore` all need conformance tests against fixtures and the reference CLI; the CLI itself need not ship. Do not run a third-party CLI on the host as an invisible fallback.

**Ship first:** a configured or default image, a bounded Dockerfile build, same-path workspace, safe named mounts, environment/user selection, limited port forwarding and reviewed container lifecycle commands. Reject unsupported non-default semantics, including unknown execution-affecting fields, while documenting harmless customizations. Defer Features and Compose until their full approved subsets are tested. With no config use an enterprise-approved BelloCode default image and current workspace settings; optionally let the agent propose a `.devcontainer` and explain its effects for the person to review, approve and commit. Do not create or commit one automatically. Treat changes to config, Dockerfile, Feature digest or mount/secret requests as a new review and recreate safely.

## 2. Dual-environment edge cases and agent contract

The authoritative source tree is host-visible; opencode reads/writes files there, but the shell, terminals, setup and project tools run in the Linux workspace. BelloCode's own Git and opencode Git shim already use sandboxed host Git with hooks and filters disabled; project shell `git` is a separate Linux Git with different policy. See [Git configuration](https://git-scm.com/docs/git-config), [worktrees](https://git-scm.com/docs/git-worktree), [VS Code environment docs](https://code.visualstudio.com/remote/advancedcontainers/environment-variables), and [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/).

| Boundary / symptom | BelloCode fix and agent guidance |
| --- | --- |
| Git ownership | Linux Git reports `dubious ownership` when ownership and process UID differ. Diagnose the actual mounted owner and Git user; fix user/mount mapping first. If necessary scope `safe.directory` to the exact validated repository and worktree, never `*`; do not change global host config. |
| Identity/config/credentials | Host commit identity, credential helper and includes may differ from container; commits may use the wrong author or push fails. Prefer BelloCode's confined host Git UI for stage/commit/push. Show identity and provenance; never copy host Git config or credential stores into the workspace. A separately approved, scoped short-lived credential is required for container Git network operations. |
| Hooks, Husky, lint-staged | Host Git intentionally suppresses hooks and external filters; container Git may run repository hooks, whose dependencies and side effects differ. Never claim a host UI commit ran hooks. Run approved checks explicitly in the container; do not enable host hooks to repair a failed workflow. |
| Worktrees / submodules | A `.git` file or submodule gitdir can point to an absolute host path inaccessible in the container; `not a git repository` results. Validate and narrowly mount the common Git directory and worktree paths at matching absolute paths, including nested submodule metadata; if outside approved/shared roots, block container Git with a specific explanation. Never rewrite shared gitdir pointers to a Linux-only path. |
| Line endings / modes / LFS | macOS/Linux `core.autocrlf`, `.gitattributes`, `core.filemode` and mount semantics can generate noisy diffs or lose executability. Honor repository attributes and compare actual modes; do not globally rewrite files. Host Git blocks external LFS filters and can show pointer content; use an approved container LFS workflow and credential path when real LFS objects are needed. Surface submodule initialization and network authorization explicitly. |
| File ownership / permissions | A root container or incompatible UID can make output unwritable or produce Git warnings. Prefer a tested non-root user and volume ownership, probe create/read/write in both directions and show actual mapping. Do not recursively `chown` a host project as an automatic fix. |
| Paths | A container-only workspace path makes host file tools, error links and Git worktree pointers disagree. Preserve absolute paths initially; later map each approved mount in both directions, including realpath/symlink validation, working directory, diagnostics and worktrees. Never guess a mapping. |
| Watches / reload | macOS writes may not generate Linux inotify events through VM sharing; stale hot reload or missed changes result. Keep the FSEvents-to-container bridge, coalesce and bound it, rescan on overflow/reconnect, and disclose that some tools need polling. Avoid pretending a touch bridge guarantees every watcher semantic. |
| Dependencies / build outputs | macOS and Linux arm64/amd64 native modules, venvs and binaries are incompatible despite identical paths. Keep platform-specific dependency trees and caches in named volumes or separate paths; Linux commands use Linux artifacts, host tools must not load them. Check tools that expect to inspect these paths and report hidden/absent output. |
| LSP / formatters | Host opencode could spawn project binaries or load incompatible dependencies. Current integration disables them and flags host configuration; keep them disabled until explicitly routed into the workspace with correct path, ownership and cancellation handling. Use container commands for diagnostics and formatting. |
| Ports / localhost | Container `localhost` is the workspace; Mac/WKWebView/host Chrome `localhost` is the Mac. A service may need to listen on a reachable container interface; explicitly forward its port to Mac loopback and give the agent the actual URL. A sibling service name is project-network DNS, not a Mac hostname. Never expose an arbitrary port publicly. |
| Environment / `.env` | Container, exec and browser environments differ; a checked-in `.env`, Compose interpolation and shell-exported variables have distinct scopes. Show variable names and sources, not values; require explicit injection and reject unresolved substitutions. Avoid importing host environment or assuming browser requests inherit shell variables. |
| Company CA / TLS interception | A transparent proxy requires trust even without proxy environment variables. Install the enterprise public root from a managed source into the container OS trust store and separately configure runtimes/package managers with their own stores (e.g. Java, Node or Python as applicable). Never disable TLS verification. Registry/daemon trust and Dockerfile `RUN` build-stage trust are separate from the running container; bootstrap an approved CA-enabled base or supported BuildKit trust/secret mechanism for **each stage**, and verify package-manager behavior. CA rotation, rebuild and interception test endpoints require enterprise validation. [Docker CA guidance](https://docs.docker.com/engine/network/ca-certs/). |
| Secrets | A build arg, Dockerfile `ENV`, image layer, shared `.env`, log or persistent exec environment can disclose a token. Keep Keychain-held secrets out of config and logs; retain the approved one-use `secret_exec` path, with its read-only project and no-network limits. Broader secret-dependent network/build workflows require a separate scoped, expiring broker or verified BuildKit secret mount, approval, cleanup and leak tests; no automatic fallback to env vars. [Build secrets](https://docs.docker.com/build/building/secrets/). |
| Docker from workspace / nested Compose | A raw daemon socket can control the host VM and defeat isolation. A future authenticated, filtered Engine proxy must enforce project ownership, image/build and network policy, mount source/target restrictions, resource quotas and cleanup **on every API operation**, including exec, build contexts and hijacked streams. Never expose the raw socket. Container Docker/Compose CLIs need explicit installation and tested API compatibility; nested stacks may require unsupported API calls and must fail visibly. Until the proxy exists, commands are unavailable. |
| Caches | Cross-project or cross-architecture caches can contain incompatible binaries or untrusted executable content. Default to named per-project, per-platform caches with explicit sharing and size/retention controls; warn before deletion. |
| Time / locale | Different `TZ`, locale and installed locale data cause divergent tests and formatting. Set approved nonsecret values deliberately, ensure image support and report effective settings; keep clocks synchronized by runtime. |
| Resources / Apple Silicon | VM and per-container CPU, RAM, disk and architecture constrain builds; OOM and slow emulation look like project failures. Show limits and image platform, prefer Linux arm64, disclose amd64 emulation and require an available compatible runtime; never promise Rosetta/QEMU or GPU support without a probe. |

**Suggested session instruction** (populate placeholders from observed state; do not insert secrets):

> Project `{project}`, branch `{branch}`, worktree `{host_path}`; workspace `{container_path}`, image `{digest}`, platform `{platform}`, user `{user}`. You edit files through host file tools; all project commands, tests, scripts, formatters, language tools and terminals run in the workspace via BelloCode. Never run project code on the Mac or fall back to the host when the workspace is unavailable. Paths are `{mapping}`; ask when a path or worktree is not mounted. BelloCode's Git UI uses confined host Git with hooks and external filters disabled; shell Git is Linux Git with separate identity, credentials and hooks. Prefer the Git UI for stage/commit/push; run required checks explicitly in the container, and never broaden Git trust or copy host credentials. Linux dependencies and build outputs are container-specific. Container localhost is not Mac localhost: use the reported loopback forwarded URL `{ports}` for the built-in browser or Chrome. Use only reported nonsecret environment settings; request approved secret access without printing values. Trust the managed company CA; never disable certificate verification. The Docker endpoint is `{available_or_unavailable}` and is policy-filtered when available; do not seek the host socket. If a mount, permission, watch, tool, port or certificate is unavailable, report the precise blocker rather than guessing or retrying on the host.

## 3. Chrome and real `browse`

[`browse`](https://github.com/anomalyco/browse/tree/e1e3b75bc153067020d74e06770750212c9f7e33) is an MCP server and relay plus a Manifest V3 extension, distinct from opencode's `experimental.browser` RPC. The [manifest](https://github.com/anomalyco/browse/blob/e1e3b75bc153067020d74e06770750212c9f7e33/public/manifest.json) requests `debugger`; [source](https://github.com/anomalyco/browse/blob/e1e3b75bc153067020d74e06770750212c9f7e33/src/background/debugger-hub.ts) uses `chrome.debugger`, which exposes CDP with Chrome restrictions ([Chrome API](https://developer.chrome.com/docs/extensions/reference/api/debugger)). Its [README](https://github.com/anomalyco/browse/blob/e1e3b75bc153067020d74e06770750212c9f7e33/README.md) documents pairing, per-browser keys, tab groups, handoff and relay updates. It can access powerful authenticated browser context; human approval and clear visibility are required, including revocation and what is shared.

| Option | Assessment |
| --- | --- |
| **a. Real host Chrome + browse** | Most direct path to the actual browse MCP tools, real logins and extensions. `browse mcp` and its native relay are host executables; they are vendor tooling, not repository project code, but **still run code on the host** and require an explicit enterprise exception to the host-executable policy. Package/pin/verify the binary and extension; prohibit installer scripts, automatic config edits and unreviewed self-updates. Existing global MCP refusal means BelloCode needs a narrowly scoped, approved host-MCP exception or a carefully controlled client-MCP bridge; do not present current project-MCP routing as supporting it. Confirm pairing, relay lifecycle, version negotiation, bounded stdio, reconnect, approval per server and session/tab scope. Real profile access and extension upgrades are the key risks. |
| **b. Dedicated Chrome or Chrome for Testing profile on host** | Same real extension and MCP; a separate app-owned profile reduces exposure to personal sessions, but needs separate sign-in and remains a host browser/tool exception. Launch a separately installed, enterprise-approved Chrome or pinned [Chrome for Testing](https://developer.chrome.com/blog/chrome-for-testing/) with isolated user-data directory; verify extension installation, enterprise policy, updates and pairing. Use a separate window adjacent to BelloCode; embedding/docking another app's interactive window is not a supported assumption. Key risk: profile security, installation/update policy and human authentication friction. |
| **c. CEF embedded Chromium** | CEF's [browser API](https://github.com/chromiumembedded/cef/blob/master/include/cef_browser.h) exposes `SendDevToolsMessage`, `ExecuteDevToolsMethod` and observers, so a separate implementation of opencode's v4 bridge is plausible. opencode desktop's [Electron CDP adapter](https://github.com/anomalyco/opencode/blob/v2.3.0/packages/gui-plugins/src/browser/cdp.ts) uses `webContents.debugger`; its [browser RPC](https://github.com/anomalyco/opencode/blob/v2.3.0/packages/plugin-browser/src/rpc.ts) includes more than CDP, including trace and Lighthouse. CDP alone does **not** prove full fidelity: implement and test every operation, file transfer, dialog, permissions, target/session, network and Lighthouse dependency. CEF [Chrome bootstrap vs Alloy style](https://github.com/chromiumembedded/cef/issues/3685): Alloy bootstrap was removed in M128; Alloy-style windows can use Chrome bootstrap. Do not equate Alloy window style with an old bootstrap. CEF [extension source](https://github.com/chromiumembedded/cef/tree/master/libcef/browser/chrome/extensions) and [extension issue](https://github.com/chromiumembedded/cef/issues/3444) show extension support exists, but browse's MV3 service worker, Chrome Web Store install, permissions, `chrome.debugger`, tab groups and UI in a particular CEF build are **unverified**. Direct CDP would implement the opencode bridge, not the real browse extension/MCP. Previous research estimates 150–250 MB, not a measured current distribution; expect helper signing/notarization, Chromium security updates and memory costs. |
| **d. Container Chrome + live view** | Headless Chrome plus Playwright/CDP is feasible in principle; displaying an interactive, low-latency live view also needs a streaming/input stack, authentication, focus, clipboard and download policy. Actual browse requires a supported extension-capable Chrome/profile and relay setup; headless extension/pairing compatibility is unverified. Container browser has separate authentication and does not provide the user's existing host Chrome state. Adds image and resource cost. |
| **e. WKWebView + browse in Chrome** | Keep the existing built-in browser for loopback previews and its v4 bridge; use approved external Chrome + browse for real-Chrome, authenticated or Chrome-specific work. The two tool surfaces and tab inventories are distinct; tell the agent which is active. WKWebView's reduced network and profiling support remains as documented. |

**Recommendation:** (e), with (a) explicitly enabled per approved MCP server and clear pairing, scope, status, stop and revoke controls. Default to an isolated Chrome profile (b) if the enterprise prefers separation; allow the real profile only with explicit consent. **Fallback:** current WKWebView bridge alone when host browse/Chrome exception is not approved; its key risk is missing Chrome behavior and reduced network/profiling fidelity, so it cannot be advertised as real browse. CEF is a later measured spike, not a prerequisite or a proven browse-compatible replacement. No host MCP, extension, Chrome or CEF integration was exercised in this research.

## 4. Target architecture, migration and decisions

| Stage | Change and acceptance gate |
| --- | --- |
| 0. Inventory and policy | Inspect representative checked-in configurations without executing them; classify unsupported fields, host commands, Feature sources, Compose, trust roots and image/build needs. Get enterprise approval for binary, MCP, CA, network and mount policies. |
| 1. Resolver / review | `EnvironmentService` adds a versioned, immutable effective-environment plan: config provenance, substitutions, image/build inputs, mounts, identities, lifecycle, ports, permissions and diagnostics. Recompute on config/metadata change with generation checks; review before code runs. Existing project without config uses the approved default. |
| 2. Workspace application | Existing Engine client builds/pulls/creates one managed workspace and keeps supervision, resource limits, network, watch bridge, secrets and per-project ownership. `bellocode-exec` consumes the validated mapping, remote user/env and readiness generation; all shell/PTY/MCP paths refuse while stale or unsupported. Never use host fallback. |
| 3. Surface and context | Environment pane shows config source, effective image/digest, user, paths, lifecycle approvals, ports, CA, features and unsupported/refused settings; show project/branch/worktree and degraded states. Settings holds enterprise defaults, trust, image and MCP policies; managed settings win. Publish the environment contract per session and refresh after changes. Preserve Git sandbox and built-in browser behavior. |
| 4. Expand with gates | Add a tested Compose workspace subset, then approved Features and lifecycle variants; add a filtered Docker endpoint only after adversarial API tests. Add separately approved browse host exception with profile pairing and stop/revoke. Test worktrees, UID mapping, proxy/CA across build/runtime/package managers, secret leakage, crash/reconnect, watcher overflow, port isolation and reference-CLI fixture parity. Run UX checklist before implementation is declared done. |

| Owner decision | Recommended default |
| --- | --- |
| Host executable exception for browse and Chrome? | Permit signed/pinned enterprise-approved tooling only; no repository code or installer on host. Without approval use WKWebView. |
| Browser profile and sharing? | Dedicated profile; explicit approval for the MCP server and each exposure of a real signed-in profile; visible stop/revoke. |
| Dev Container coverage and migration? | Safe image/Dockerfile subset first, reject unsupported behavior; default image for projects without config, proposal and user approval for committed config. |
| Host initialization and lifecycle? | Never execute `initializeCommand`; review container lifecycle commands before use. |
| Compose, Features and privilege? | Defer Compose workspace and Features; deny privileged, added capabilities, unrestricted mounts and host socket. |
| Git, credentials and hooks? | Preserve confined host Git; show hooks suppressed; approved checks in container, scoped temporary credentials only when needed. |
| Corporate trust and egress? | Managed public CA, verified separately for daemon/build stages/runtime/package managers; security team supplies rotation and validation procedure. |
| Secrets and Docker proxy? | Keep one-shot secret path; design broader network/build secret access and filtered Docker proxy with security before enabling. |
| Resource and architecture baseline? | Per-project limits and arm64 by default; explicitly report emulation and unavailable resources. |
| CA/Feature/image provenance and updates? | Approved registries, pinned Feature and browse artifacts, reviewable updates; use existing image policy, no unsupported signature claims. |

**Unverified:** this research performed no build, tests, containers, runtime access or UI exercise. Native Dev Container conformance, image metadata merges, BuildKit transport/trust and registry policy enforcement, actual Rancher mount/UID/watch behavior, Feature installation, Compose parity, CEF extension support, host browse pairing and managed enterprise CA behavior all require dedicated fixtures or spikes. The CEF size estimate was not independently measured; no compatibility claim implies security approval.
