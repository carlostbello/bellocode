# Containers and Rancher for BelloCode

Research, 2026-11-16. Scope: opencode **2.3.0**, self-managed GitLab, one enterprise. “Rancher” is ambiguous: **Rancher Desktop** is a local Linux VM and container runtime on the Mac; **Rancher Manager** manages clusters and access to their Kubernetes APIs. They are different integration targets and neither implies the other. Findings below distinguish source inspection from an end-to-end test. No container or cluster was started for this research.

## 1. What can run in containers?

| Option | Boundary and host access | Experience, latency and offline | Policy implications |
| --- | --- | --- | --- |
| **A. Tool execution only** | Host app and opencode; route shell/test/dev-server execution to one project or thread container. Built-in file tools, plugins, PTYs and setup paths may still operate on the host. Writable project mounts permit changes to those host files; runtime sockets or extra mounts widen access. | Closest to current app; local UI and file operations are fast, but mapping cwd, signals, output, processes and terminals is complex. Cached images work offline, subject to model access. | Does **not** prove no untrusted host execution. A shell wrapper alone is bypassable; enforce every execution path and treat host-side plugins and hooks as code. |
| **B. Server in local container** | Swift UI stays on macOS; Linux opencode, shell, file tools, PTYs and server plugins run in a project/thread container. Only explicitly mounted host paths are exposed; the runtime socket and broad home mounts defeat the boundary. | A single execution environment and native opencode PTY semantics; needs path translation, lifetime and storage design. Bind-mount metadata/file-watching overhead may be substantial. Local runtime and cached images can work offline; remote models still need network. | Fastest plausible path to containerizing the agent and its ordinary tools, but writable source is exposed and a container alone is not a complete security boundary. Devcontainer lifecycle scripts and dependencies run as code inside it. |
| **C. Server in cluster pod** | Agent and source live in a pod, ideally per thread, with PVC or ephemeral volume; host sees only explicit client channels. Clone GitLab or sync source; local uncommitted changes require an explicit transfer and conflict policy. | Network RTT affects every request, stream and terminal; startup, image pull and PVC provisioning add delay. Cluster/connection outage prevents execution; cached UI may remain readable. Suitable for centrally controlled compute, not local offline work. | Stronger central admission, isolation and audit possibilities; pod security, network policies, RBAC, storage, tenancy and cluster security determine actual boundary. |
| **D. Dev Container definition** | `devcontainer.json` describes the environment; it is not a runtime or isolation mechanism. Apply it to B or, with a compatible implementation, C. Image/build, features, mounts, lifecycle commands, remote user and forwarded ports all affect execution. | Reproducible team setup, but builds/pulls and lifecycle scripts cost time; cached artifacts help offline. Arbitrary features, Compose and host requirements may exceed an initial implementation. | Treat the file and its scripts as untrusted project input; policy must validate the **resolved** image, mounts, features, privilege and networking before creation, and prevent bypass at the runtime/admission layer. [Specification](https://containers.dev/implementors/spec/), [properties](https://containers.dev/implementors/json_reference/). |

For B, the bundle's macOS arm64 executable cannot execute in Linux: pin and verify a compatible Linux arm64 opencode 2.3.0 build and its Linux PTY/helper dependencies in an approved image; amd64 needs matching compute or emulation. One existing server serves all directories; per-thread isolation changes server/session topology, cross-thread orchestration and durable storage. A per-project server is less disruptive but shares trust and processes among threads. A project bind mount is writable by design: other host files are excluded only if they are not exposed by mounts, credentials, sockets, or bridges. Containers do not protect against kernel/runtime vulnerabilities or exfiltration over allowed network.

Git worktrees can point through `.git` files to a common Git directory outside the mounted worktree. Mount the required common directory deliberately or create worktrees **inside** a container-owned repository; test permissions, symlinks, case sensitivity and cleanup. Map host and container paths for file links, location-scoped API requests, diff and Git operations; remote-only files need a file-access abstraction, not a fabricated host path. Source-of-truth and conflicts for unsaved local edits must be explicit. Linux file events over macOS VM sharing may differ from native FSEvents; test watchers and rescan/reconcile on gaps. Measure real repo workloads before choosing bind mounts versus a VM volume plus sync.

Provider credentials currently live with opencode data: a container has no macOS Keychain. Provision minimum, scoped, revocable credentials through an approved broker or protected short-lived injection; do not bake into images, logs or shared volumes. GitLab API token stays in Keychain for Swift API calls; Git clone/fetch/push inside an environment needs separate scoped Git authentication and an approved delivery mechanism. No host forge CLI is required. Model APIs, GitLab, registries and package repositories need explicit egress; offline use depends on a reachable local model and cached dependencies.

A container's `localhost` is not the Mac's. Bind a dev server to an appropriate container interface, publish only selected ports on host loopback, and translate preview URLs before WKWebView opens them. Treat forwarded pages as untrusted: WKWebView runs on the Mac and can access what its own network context permits. The existing browser v4 bridge and client-MCP are client-initiated channels to the server; package the server plugin inside the image, authenticate those channels, and test reconnect and attachment across the new boundary. A reverse callback to host loopback or a Unix socket does **not** automatically work from a container. Browser downloads/uploads and file paths need explicit mapping. Shared browser control is a separate host capability, not contained by moving the server.

Common enterprise controls to agree with security: no host execution of untrusted project code; immutable digest-pinned images from an internal registry, scanning and provenance; non-root, no privileged mode, host PID/network, runtime socket or unrestricted host mounts; resource limits; controlled network egress and secrets; auditable identity, actions and retention. These are proposed controls, not a claim of this company's policy. Enforce them outside the agent's control; app approval rules alone are not a security boundary.

## 2. What opencode 2.3.0 provides

Pinned source inspected at [`0ac0d7e`](https://github.com/anomalyco/opencode/tree/0ac0d7e), the 2.3.0 commit identified in [05-opencode-integration.md](05-opencode-integration.md). The version-specific repository contract remains authoritative; current public opencode documentation may describe a different major version.

- **Attach:** the existing HTTP/SSE client can connect to a separately started server; `opencode` also has pairing/remote support and `serve` network options as recorded in [05](05-opencode-integration.md). Connection is not the same as supervising a child or provisioning a container. Bind narrowly, use authentication and TLS or a trusted authenticated tunnel; never expose an unauthenticated server publicly. Validate Basic auth, all WebSocket routes, SSE resync, pairing and server version on the target. The existing `--stdio` parent-EOF lifetime cannot simply be assumed for a remote service.
- **Shell:** [`shell.ts`](https://github.com/anomalyco/opencode/blob/0ac0d7e/packages/core/src/shell.ts) constructs command, cwd, shell and environment and invokes `shell.create.before` before spawn; the [hook type](https://github.com/anomalyco/opencode/blob/0ac0d7e/packages/plugin/src/effect/shell.ts) exposes mutable fields. [Shell selection](https://github.com/anomalyco/opencode/blob/0ac0d7e/packages/core/src/shell/select.ts) resolves configuration and `$SHELL` subject to compatibility. A plugin could transform an invocation or provide a replacement tool; quoting, cwd, cancellation, background jobs, output and policy require testing. A configured shell is not a general arbitrary command-executor API and wrapping it does not isolate all host paths.
- **Environment:** shell jobs use session variables if present, otherwise process environment, then hook edits; the [session environment store](https://github.com/anomalyco/opencode/blob/0ac0d7e/packages/core/src/session/environment.ts) is in memory. `PUT /api/session/{id}/environment` is in the pinned contract; check its exact payload and replacement/lifetime behavior before use. PTY creation separately merges process environment and input env. Environment variables can be visible to processes and may leak into output; do not claim secret isolation.
- **PTY:** [PTY creation](https://github.com/anomalyco/opencode/blob/0ac0d7e/packages/core/src/pty.ts) spawns the requested command or selected shell locally to the server, with cwd and env. A client can request a command/arguments, but putting a runtime CLI there is not a native container transport, and persistent PTYs/shell jobs are separate paths. Verify resize, signals, reconnect, shell quoting and persistent terminals. With B/C, the server and PTYs naturally run inside the container/pod.
- **Plugins:** [`tool.execute.before`](https://github.com/anomalyco/opencode/blob/0ac0d7e/packages/plugin/src/effect/tool.ts) can modify input or reject with a tool error; tool transforms can remove/add/update tools. `shell.create.before` modifies invocation fields, but its hook has no failure channel. These are useful instrumentation/policy hooks, not containment; plugin code runs with server authority. Client MCP and browser bridge remain experimental and require contract tests.
- **Sandbox/workspace:** the source contains an internal [workspace driver](https://github.com/anomalyco/opencode/blob/0ac0d7e/packages/core/src/workspace/driver.ts) and [SDK embed registration](https://github.com/anomalyco/opencode/blob/0ac0d7e/packages/sdk/src/internal/host.ts); its default registry is empty. This is evidence of an extensibility mechanism, **not** evidence that the shipped CLI has a usable container provider or stable plugin API. Project `sandboxes` in this codebase refer to worktree locations, not proof of security sandboxing. No turnkey container sandbox or universal external command-runner setting was verified in the pinned server; exhaustive absence is not proved.

## 3. Rancher Desktop on macOS

[Container engine settings](https://docs.rancherdesktop.io/ui/preferences/container-engine/general/) distinguish **dockerd/moby** (Docker-compatible API) and **containerd** (typically `nerdctl`). Switching engines changes available images/workloads; don't switch it on the user's behalf. Detect installation and a usable service independently: app/CLI presence alone does not prove the VM is running. This machine, read-only check: `/Applications/Rancher Desktop.app`, `~/.rd`, `~/.rd/docker.sock` and `/var/run/docker.sock` absent; `docker` and `kubectl` are on PATH; `rdctl` and `nerdctl` were not found. This is not proof that no other runtime exists. No sockets were connected to and no settings read.

- **Discovery and state:** [rdctl reference](https://docs.rancherdesktop.io/references/rdctl-command-reference/) documents status/settings and `rdctl api` access to the local management API. API endpoint, authentication, version and stability must be discovered from the installed version's documentation, not hardcoded; native Swift HTTP may be possible once that contract is verified. `rdctl` is an optional host CLI fallback subject to enterprise approval, not a requirement for Docker API operations. Read-only probing must not implicitly start the VM or change settings.
- **Dockerd:** Rancher Desktop documents user-level `~/.rd/docker.sock` and, depending on administrative access, `/var/run/docker.sock`; use the configured endpoint, verify identity and permissions rather than assuming the global socket belongs to Rancher. Swift can implement HTTP/1.1 over `AF_UNIX` (e.g. Network.framework or a maintained transport) and negotiate the [Docker Engine API](https://docs.docker.com/reference/api/engine/version/v1.47/): ping/version, list, pull, create, start, inspect, logs, exec, stop and remove. Upgrade/hijacked streams, framing and cancellation need explicit implementation. A Docker socket grants powerful control of its daemon; never mount it into an agent workspace.
- **containerd:** [nerdctl](https://github.com/containerd/nerdctl) is a Docker-compatible CLI, not a Docker Engine API endpoint. containerd exposes gRPC and Kubernetes CRI services in the VM ([architecture](https://github.com/containerd/containerd/blob/main/docs/cri/architecture.md)); a Swift gRPC client is theoretically possible but discovering/reaching a supported macOS endpoint, namespaces, image unpacking, networking, snapshots and lifecycle support is **unverified**. CRI is Kubernetes' runtime interface, not a portable drop-in Docker API. For a first release require dockerd or an explicitly approved, pinned `nerdctl` integration; do not claim direct containerd support without a working prototype. No host Docker CLI is needed for the dockerd API.
- **Registry:** Docker image pull API accepts registry auth via `X-Registry-Auth`; obtain scoped credentials from Keychain, encode only in memory, never log headers or daemon responses containing secrets, and validate the image digest after pull. Native credential-helper invocation is a host CLI dependency; avoid it if policy forbids it. Image pulls may be satisfied from cache offline; handle expiry, CA trust, proxy and registry failures. Cluster image pulls use Kubernetes `imagePullSecrets` or workload identity instead, subject to cluster policy.
- **Mounts/resources/ports:** [volume settings](https://docs.rancherdesktop.io/ui/preferences/virtual-machine/volumes/) describe VM-type-dependent sharing, including virtiofs where supported. Performance and watcher behavior depend on RD version, VM, mount implementation and workload; benchmark, do not promise equivalence to native APFS. Docker create API supplies bind mounts, CPU/memory limits and port bindings; VM limits remain a ceiling. Publish previews on `127.0.0.1` and allocate ports safely, show mappings and tear them down. Ensure the application listens on a reachable container interface. Prefer named VM volumes for heavy dependency trees, with an explicit sync strategy.
- **Local Kubernetes:** optional Rancher Desktop k3s supplies a kubeconfig/context. A native Kubernetes HTTPS client can use an explicitly selected context and CA/auth data without `kubectl`, but kubeconfig `exec` credential plugins would launch a host CLI: reject or require explicit enterprise approval. Do not rewrite the user's kubeconfig. Distinguish local k3s from a remote Rancher-managed cluster and show the selected context.

## 4. Rancher Manager and Kubernetes

Use the [Rancher API quickstart](https://ranchermanager.docs.rancher.com/api/quickstart) and [API tokens](https://ranchermanager.docs.rancher.com/api/api-tokens); store a scoped, expiring Rancher token in Keychain, keep TLS verification enabled and honor enterprise CA policy. List only clusters and Rancher projects the identity can access; Rancher projects group namespaces and are not Kubernetes projects. Enumerate namespaces via the selected cluster's Kubernetes API and RBAC. Discover version-specific endpoints/schema from the deployed Manager rather than hardcoding unverified responses. Rancher's [kubeconfig guidance](https://ranchermanager.docs.rancher.com/how-to-guides/new-user-guides/manage-clusters/access-clusters/use-kubectl-and-kubeconfig) covers generated configs and authentication; a config can target the Rancher proxy or an authorized direct endpoint. Treat kubeconfig tokens and certificates as secrets, and reject unsupported exec plugins rather than silently executing them. Token lifetime, proxy streaming support and exact API routes must be verified against the enterprise deployment.

A proposed flow, entirely possible without `kubectl` **if** its required authentication and streaming protocols are supported by the selected endpoint:

1. Select cluster, Rancher project and namespace, check authorization and quotas. Create an owned, labelled workspace PVC and a restricted pod using the Kubernetes HTTPS API; use a digest-pinned image with Linux opencode and the plugin. Clone GitLab in the pod using short-lived scoped credentials, or explicitly sync source and resolve conflicts. A PVC's lifecycle is independent of a pod; retain/delete it only according to a visible policy. Choose per-thread or shared-project tenancy, capacity and cleanup/TTL; handle retries idempotently and reconcile leaked resources after crashes.
2. Run `opencode serve` inside the pod with a protected data directory; access its HTTP/SSE/WebSocket endpoint over an authenticated tunnel or Kubernetes port-forward, with server auth and no public Service by default. Confirm how Basic auth, connection upgrade, reconnect, health and per-session state behave. Cluster availability and model-provider egress are prerequisites.
3. Use [Pod API connect operations](https://kubernetes.io/docs/reference/kubernetes-api/core/pod-v1/) for `exec`, `attach`, logs and `portforward`. Kubernetes streaming uses upgraded multiplexed connections; [WebSocket transition details](https://kubernetes.io/blog/2024/08/20/websockets-transition/) explain version-dependent WebSocket/SPDY support. Implement and test negotiated protocols, channels, terminal resize, close/error handling, backpressure and cancellation in Swift; URLSession support for the required upgrade through the Rancher proxy is **unverified**, and SPDY fallback may require a dedicated library. No `kubectl` is intrinsically required, but no working Swift implementation is established here.
4. Forward an explicitly chosen pod port to Mac loopback for WKWebView; avoid automatically exposing arbitrary ports or a wildcard listener. Kubernetes RBAC must separately authorize `pods`, `pods/log`, `pods/exec`, `pods/attach`, `pods/portforward`, PVCs and their relevant verbs; Rancher authorization and cluster admission can still deny requests. Show source, namespace, identity, status and connection failures. Record create, exec, forwarding and cleanup without credentials or command output in logs.

Kubernetes security needs admission controls, Pod Security restrictions, non-root identity, dropped capabilities, seccomp, no privilege escalation/host namespaces/hostPath, quotas, network policy enforced by the CNI, isolated service accounts and short-lived credentials. Cluster administrators must apply these; a pod is not a VM-grade boundary by itself. Design container survival, session data retention, PVC encryption/backups, orphan collection and cluster-side audit with the platform team. [Kubernetes API concepts](https://kubernetes.io/docs/reference/using-api/api-concepts/) and [Pod API](https://kubernetes.io/docs/reference/kubernetes-api/core/pod-v1/) define the underlying resources.

## 5. Product surface, smallest to largest

1. **Runtime status:** display detected Rancher Desktop engine, reachability and selected socket, or selected Manager/cluster/namespace; show offline, unauthorized and unsupported states. Detection is read-only.
2. **Project environment:** explicit Host / Container image / Dev Container / Cluster workspace, with runtime, image digest, project, branch, worktree, filesystem location and isolation scope always visible. Host is a policy-controlled exception, not an automatic fallback when a container fails. Persist selection and expose status/accessibility/keyboard commands.
3. **Workloads panel:** list only resources bearing BelloCode's ownership and project labels; show image, state, limits and logs; user can exec into a terminal tab, stop or restart. Never imply ownership from a label alone for destructive operations; reconcile identity and resource ID. Cleanup and PVC retention are explicit.
4. **Agent tools:** narrow inspect/list/log and management tools with per-action approval, project and identity attribution, deny cross-project access by default, and no agent self-approval. Enforce actual privileges using scoped Docker access or cluster RBAC/admission; the agent must not receive a general runtime socket or administrator credential.
5. **Previews:** discover or request a port, ask before publishing where required, bind loopback, open the forwarded URL in the existing browser, and show origin and active forwards; terminate on workspace close. Make remote `localhost` translation explicit to the agent and user.
6. **Policy and audit:** centrally provision allowlisted registries/digests, signature/scanning requirements, mount, egress, resource and environment rules. Record actor, project, thread, server/workspace ID, image digest, cluster/namespace, action, decision, outcome and time; do not record tokens, source or output by default. Local records are not tamper-proof; send to an enterprise-controlled audit sink if required and approved.

## 6. Recommendation, decisions and first spike

**Default recommendation:** start with Rancher Desktop **dockerd**, one approved Linux opencode server container per project, with a narrowly scoped source bind mount and loopback-only API/preview ports. It preserves opencode's ordinary execution and PTY paths and is the shortest plausible route to putting the agent and its tools in a container. It is an architectural change to the present single host server, not a configuration toggle. It does not containerize the macOS UI/browser, prevent modification of mounted files, or by itself meet a strict enterprise isolation policy. If the owner means managed clusters, prioritize the pod design instead; do not present Desktop status as Manager integration. If policy forbids writable host mounts or untrusted project code influencing host files, use a container-owned clone and explicit reviewed sync, or a cluster workspace, rather than promising compliance from a bind mount.

| Phase | Outcome and gate |
| --- | --- |
| 0. Policy and spike | Agree on threat model and target runtime; run the small end-to-end spike below before changing the architecture. |
| 1. Local container | Docker Engine API integration, Linux pinned image, isolated opencode data, local auth, project path mapping, scoped mounts, loopback previews, lifecycle and recovery. Contract-test all channels and explicit no-host-fallback. Build a clear status/environment selector. |
| 2. Reproducibility and controls | Implement a documented, policy-validated **subset** of Dev Containers first; reject unsupported fields instead of silently ignoring them. Add registry identity/digest enforcement, limits, audit, and workload UI. Expand spec coverage only with tests. |
| 3. Cluster | Add Rancher authentication, selected Kubernetes context and pod/PVC lifecycle, native streaming and forwarding after platform security and streaming spike pass. Add remote file/diff/Git and reconciliation semantics. |
| 4. Broaden | Consider per-thread servers, containerd-native support and richer workload tools once user demand and isolation tests justify them. |

**Owner decisions, with defaults pending confirmation:**

1. Does Rancher mean Desktop, Manager, or both? **Default:** Desktop first; Manager separately. Which versions and supported macOS/CPU architectures?
2. Does “everything” include the app/browser, or agent server, all project code and tools? Is writable host source allowed? **Default:** native app/browser; containerize server and project execution, mount only selected project; security must approve.
3. Is host execution permitted at all, including setup scripts, Git, host plugins, credential helpers and Dev Container helpers? **Default:** no untrusted project code on host; no automatic host fallback. Existing app-host Git/worktree operations require an explicit audit and migration.
4. Isolation granularity and persistence: project or thread; shared source, per-thread clone/worktree, and retention? **Default:** per project for first spike, persistent data and explicit cleanup; threads share its trust boundary.
5. Engine and host CLI policy: dockerd, containerd or local k3s; are `rdctl`, `nerdctl`, `kubectl`, Docker credential helpers or devcontainer CLI allowed? **Default:** dockerd API, no host CLI requirement; reject unsupported modes visibly.
6. Approved image registry/digests, Linux architectures, base image, scanning, signing and allowed Dev Container features/scripts? **Default:** internal digest-pinned non-root image, no privilege or runtime socket; reject unapproved inputs.
7. How are GitLab Git credentials, model-provider credentials, CA certificates, registry credentials, network egress and offline model access provisioned? **Default:** scoped short-lived credentials via an approved broker, Keychain only for app-held tokens; no secrets in images or logs.
8. For Manager: which URL/version, auth and token lifetime, cluster, namespace, RBAC, network policy, storage class, quotas, PVC retention and audit sink? **Default:** no cluster provisioning until platform team supplies a restricted namespace and approves the design.
9. Are local modifications authoritative, and how are remote clone/sync conflicts and Git worktrees handled? **Default:** local bind mount for Desktop; explicit clone and conflict-aware sync for cluster, never silent overwrite.
10. Which data may the browser bridge, client MCP and agent workload tools reach, and are forwarded ports/agent actions approval-gated? **Default:** loopback-only opt-in preview, current browser sharing controls, least privilege and visible approvals for workload mutations.

**Smallest pass/fail spike:** on an approved Rancher Desktop dockerd installation, create one non-root Linux arm64 image containing the pinned server and bundled plugin; use a dedicated disposable Git repo with a worktree, an isolated data directory, and only a narrowly scoped mount. Connect from a minimal Swift client using authenticated loopback, run a real agent turn that edits a file and runs a test, open/resize/reconnect an opencode PTY, stream SSE, attach client MCP and browser v4, open a forwarded test server in WKWebView, kill/restart the server and reconcile. Confirm host paths outside the mount and the Docker socket are inaccessible; confirm Git common-dir access is explicitly scoped. Measure cold/warm create-to-ready, p50/p95 shell round trip and PTY echo over 100 samples, repo scan and watcher delivery versus host baseline, and reconnect/resync correctness. **Pass:** all functional and isolation assertions pass; zero missed final file changes after forced rescan; no duplicate/missing durable messages after restart; p95 PTY echo <100 ms locally and cold ready <10 s with image cached. Record actual numbers and deviations; otherwise stop before product implementation and revise scope. These are proposed gates, not measured results.

**Unverified:** no Rancher Desktop, Manager, cluster, runtime API, registry, Linux image or remote opencode execution was exercised. Mac sharing/watcher behavior, actual host CPU architecture, Linux binary distribution and PTY dependencies, Dev Container compatibility, Swift Unix-socket and Kubernetes streaming implementations, browser/client-MCP across a container boundary, and enterprise security approval remain open. The requested UI acceptance checklist is not applicable to this research-only file; no project build or tests were run.
