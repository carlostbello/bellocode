# Auto mode, risk visibility and secrets

Research, 2026-11-18. Upstream evidence is pinned to T3 Code commit
[`8cf97b5`](https://github.com/pingdotgg/t3code/tree/8cf97b5f06f30a872ce30ab8a888f2ff012365a2)
and opencode [`v2.3.0` / `a6b15d3`](https://github.com/anomalyco/opencode/tree/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7),
the version in `Contracts/opencode-2.3.0`. Line links below point to those revisions. This is source research, not a live security test. Owner constraints: one enterprise, GitLab at `https://gitlab.novacoast.com`, native host opencode, commands in project containers, no host forge CLI ([plan §0](../PLAN.md#0-scope-constraints-from-the-owner-2026-11-16)).

## 1. What T3 Code's Auto actually does

**There is no single T3 reviewer to reproduce.** T3 delegates review to each provider and translates its mode. Its [mode documentation](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/docs/user/permission-modes.md#L13-L32) says Auto uses the provider's automatic review for routine actions and asks about others. For Codex, the [adapter](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L737-L765) sends `approvalPolicy: on-request`, `approvalsReviewer: auto_review`, `sandboxPolicy: workspaceWrite`; this is not an AI review of every tool call. Calls already permitted by the sandbox/rules need not produce a review. Full access uses a different policy. T3 does not supply the reviewer prompt or select its model in that mapping.

The Codex-generated protocol exposes unstable risk `low/medium/high/critical`, authorization `unknown/low/medium/high`, statuses `inProgress/approved/denied/timedOut/aborted`, and decision source `agent` ([schema](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/packages/effect-codex-app-server/src/_generated/schema.gen.ts#L2902-L2944)). It represents a timeout ([schema](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/packages/effect-codex-app-server/src/_generated/schema.gen.ts#L28369-L28379)); these fields do **not** establish thresholds, confidence, a deadline, prompt, model, actual input context, or whether timeout escalates. No reviewer prompt/policy was found in T3's source to quote. The provider implementation and a live run would be needed to establish those details, and whether it inspects commands, paths, diffs or conversation. Do not infer them from the protocol. Likewise the exact automatic approval/denial criteria and a complete audit trail were not established.

Provider differences matter. Cursor passes an `autoReview` flag and sandbox setting ([adapter](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/packages/provider-cursor/src/server/adapter.ts#L196-L207)); its [guide](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/docs/user/cursor.md#L79-L85) notes Windows limitations. fx selects its native Auto and forwards remaining requests to the user ([source](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/packages/provider-fx/src/server/acpSupport.ts#L62-L84)); Grok forwards review-blocked commands. Claude and Codex use their own provider facilities. OpenCode Auto instead uses supervised rules: [provider docs](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/docs/user/providers-opencode.md#L63-L73), [adapter](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/packages/provider-opencode/src/server/adapter.ts#L637-L700). T3's adapter targets its OpenCode protocol; BelloCode must use its pinned v2 action names, not copy that adapter's `bash` rules.

The composer exposes mode and shortcut, with Full access initially default; requests appear in conversation and child requests bubble to parent ([UI description](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/docs/user/permission-modes.md#L3-L25)). I did not establish a universal visible auto-approved chip, denial presentation, or durable per-decision audit in T3; provider output differs. OpenCode's **Allow for workspace** is a saved matching grant across sessions; it may avoid subsequent prompts and thus a reviewer listening only to requests. Denial does not stop the entire turn ([provider docs](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/docs/user/providers-opencode.md#L63-L73)).

## 2. Existing protection and its gaps

For the default v2.3.0 agent the ordered rules are `*/* allow`, then `read *.env ask`, `read *.env.* ask`, `read *.env.example allow` ([schema](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/schema/src/agent.ts#L39-L51)). Build additionally allows `question`; other built-in agents have different additions, e.g. Explore's explicit set ([agent plugin](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/core/src/plugin/agent.ts#L55-L93)). Matching normally uses last rule; unmatched falls back to ask ([permission](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/core/src/permission.ts#L94-L103)). Configured denies are checked before saved project allows, then the evaluation hook runs ([permission](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/core/src/permission.ts#L159-L201)). Session rules can override default asks, and BelloCode Full access's `* allow` does exactly that ([agent-ui](../features/agent-ui.md#permission-modes-verified-with-post-apisessionidpermission-which-evaluates-without-a-prompt)). Saved grants can also suppress asks. Do not assume `external_directory` asks by default: `* allow` covers it.

File tools classify paths outside location/project and assert `external_directory` ([file access](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/core/src/file-access.ts#L90-L115), [assertion](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/core/src/file-access.ts#L120-L136)); this is a permission mechanism, not an OS sandbox. Its lexical classification is not proof against symlink/race or shell indirection. Shell commands, scripts, grep, MCP servers and tool output can expose values without a `read *.env` assertion. Other credential names, encoded values, network exfiltration, destructive git, `curl`, dependency lifecycle scripts, installs and publishing have no comprehensive default semantic protection. Container isolation protects the host only within its actual mounts and runtime threat model; it is not secret-flow control. T3 Full access similarly delegates to provider behavior; Claude has a documented dangerous-removal exception, not a general risk detector ([modes](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/docs/user/permission-modes.md#L47-L55)).

## 3. Recommended BelloCode Auto and Full access visibility

**Use both a server plugin and the app.** The plugin's v2 [`execute.before`/`execute.after`](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/plugin/src/promise/tool.ts#L44-L69) see tool name, session, call ID and input; before can reject. Its [`permission.evaluate`](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/plugin/src/promise/permission.ts#L8-L31) sees the proposed effect even after saved rules. Configure Auto to ask for shell, edit, external paths and relevant network/tool actions; use the hook to preserve mandatory gates despite saved grants, and the app to own queue, review, cards and replies. `permission.asked` alone misses allowed actions and workspace grants. Contract-test hook ordering, async waiting and coverage of built-in, MCP, shell, child and browser tools on the pinned binary before claiming enforcement. The app must resync pending requests after SSE gaps, deduplicate by request/call ID, and never race a user reply or apply a stale generation's result. When the app/plugin is unavailable, protected calls must remain pending or fail closed, not silently allow.

Policy precedence: configured hard denies first; mandatory escalation next; narrowly scoped, explicitly approved user grants next; deterministic allow next; reviewer only for the remainder. Auto replies `once`, never `always`. Saved project grants must not bypass mandatory gates or notice generation; show their scope and allow revocation. Preserve opencode agent denies. Avoid recursion by marking the reviewer session and withholding tools; enforce a bounded concurrent queue with visible overflow/escalation. `once/always/reject` and request fields are in the [v2 schema](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/schema/src/permission.ts#L26-L53).

* **Deterministic allow:** narrowly identified read-only metadata and in-project ordinary reads, and simple bounded safe edits only after canonical target checks. Unknown tools, dynamic commands, symlink ambiguity, shell expansion, opaque scripts and unclassified effects are not safe by default. An arbitrary package test is code execution, not a safe read.
* **Always escalate:** possible secret/credential read or context inclusion (including `.env`, private keys and keychain files); outside-project or cross-project access; changes to secret policy, network or isolation; network requests carrying credentials or suspected data; destructive git (`reset --hard`, clean, force push), irreversible deletes, publishing/deploying, package install/lifecycle scripts, and unknown compound commands. Hard-deny known policy violations. A model cannot override either list.
* **Reviewer:** use a dedicated isolated, tool-less opencode reviewer session with a configurable fast approved model, not the working conversation or same session. `session.generate` exists in the pinned [API](../../Contracts/opencode-2.3.0/openapi.json); verify its isolation, output schema, token accounting, persistence and cancellation before choosing it over a dedicated session. Send only bounded sanitized action, canonical project-relative targets, purpose and minimum user intent; include a bounded diff only when needed, never actual secret values or unrelated history. Each review costs a model request and adds network/model latency; record latency and token/cost metadata without content, rate-limit and cache only exact immutable decisions within a short generation. No reliable fixed price or latency is established here.
* Reviewer output is strict JSON: `allow_once` or `escalate`, reason code and short explanation; invalid, extra, ambiguous or truncated output, timeout (e.g. configurable 5 s), cancellation, offline, model error, unknown policy or budget exhaustion => escalate, never approve. Do not expose a model-supplied confidence as calibrated safety. Bind the decision to exact input hash, IDs, policy version and session generation; recheck immediately before execution and discard stale replies.
* Treat repository text, tool arguments, diffs, command output and even claimed user intent as attacker-controlled data. A fixed high-priority policy forbids following instructions in them; quote/structure and limit them, strip secrets, forbid reviewer tools, and validate output. Delimiters are not a security boundary; deterministic gates and actual isolation remain authoritative. Prompt-injection and encoded-command adversarial tests are required.

In Auto, show a compact non-blocking “Auto-approved” chip, reason and expandable audit entry; show the existing pinned approval card and Needs-you count only for escalations. Audit records include project/thread/call, timestamp, category, decision source, model/policy version, scope, outcome and reason code; bound retention and redact content/secrets. For Full access, instrument the same before/after hooks and app-managed operations to show non-blocking transcript notices for detected secret-looking reads, outside paths, network/exfil patterns, destructive git, install and publishing; surface a reviewable notice in Needs-you without claiming it is a blocked approval. Record **attempted vs completed** separately. Shell static analysis cannot see arbitrary runtime operations; monitor at the container/egress boundary where feasible and label coverage as best-effort. Host file tools, helper shell, terminals, MCP, browser, host git and service containers are separate coverage points. Exact command parsing is not a security boundary and no notice must promise complete detection.

## 4. A value the agent cannot see

Today a Keychain reference and exact-command approval avoid direct app disclosure, but the command receives the value and its output returns to the model; it may print, encode, split or write it. The one-shot container is offline/read-only by default, but permitted exceptions change that. The FIFO version is weaker ([current guarantee and limitations](../features/orchestration-extras.md#3-secrets)). opencode converts tool inputs and results into model history ([source](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/core/src/session/runner/to-llm-message.ts#L100-L135)); MCP local configuration supplies environment variables to the process ([source](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/core/src/mcp/client.ts#L462-L475)). Thus environment, MCP outputs, errors, traces, transcript and logs all need their own boundary; literal redaction alone is not a guarantee.

| Design | Actual guarantee, bypasses and cost |
| --- | --- |
| **Placeholder + TLS egress proxy** | Agent sees a random opaque placeholder only; proxy substitutes a Keychain value after authenticating project/session/capability and validating exact HTTPS destination, method, path, header and use count. A host allowlist alone is insufficient: attacker-controlled paths, redirects, open proxies and reflection can leak to the model or an attacker. Response headers/bodies, errors and compressed/encoded/chunked content may echo/transform the value; block untrusted response content or use strict structured allowlists, not literal redaction. Prevent direct egress, DNS, UDP/QUIC, IPv6, bypass proxies, alternate interfaces and proxy-env overrides at a separately enforced network boundary; reject CONNECT tunnelling, redirects and TLS verification failures; validate resolved destinations and chain to company interception correctly. A CA in the container is not itself egress enforcement. Placeholder replay and encoded/split placeholders require narrow, short-lived, non-exportable capabilities. TLS pinning and client certificates may break; proxy/CA lifecycle, streaming, HTTP/2 and audit are substantial work. A compromised bound service, network administrator or proxy can see the real credential. |
| **App-side brokered tools** | App holds secret and performs a fixed, typed operation (e.g. GitLab API or git credential exchange), never passes the value to opencode or an agent process. Enforce host, identity, method/path, parameter and response schemas; return only allowlisted non-secret fields, bounded errors/status, no raw headers/body. A server could reflect or transform a secret into an apparently allowed field, or a response may contain other sensitive data; the service and schema must be trusted and tested. Brokered MCP/service-container environment is safe only if that server is trusted and isolated, cannot disclose through results/logs/network/files, and its returned data is constrained; merely injecting an env variable is not safe. Per-operation integration and lost arbitrary CLI flexibility are the cost. |
| **Offline output-withheld one-shot** | A secret-consuming arbitrary command can be isolated with no network/DNS, no writable shared mounts, no persistent volumes, no output, logs or agent-readable artifacts, and a fixed coarse outcome after a fixed interval. Never return arbitrary exit codes, lengths, timing or resource metrics: these are covert channels (repeat attempts can encode the value). Destroy instance and cap attempts. Even then guarantees depend on kernel/VM, runtime, side-channel and other-local-client assumptions; code can attempt privilege escape. Useful for a predeclared narrow operation, but an arbitrary command with no observable result has limited utility. Existing `secret_exec` does not meet this design. |
| **OS controls** | Keychain ACLs, process isolation, sandbox/VM, filesystem permissions and network policy reduce which processes can obtain a secret. They do not hide a value from code deliberately given it, or prevent encoding and exfiltration by that code. Same-user access, Docker API clients, host and Rancher VM are explicit trust boundaries; secure enclave/non-exportable keys can sign challenges without revealing private key bytes, but cannot make an arbitrary reusable API token non-exportable. Deployment, entitlements and service protocol support are costs. |

**Recommendation:** implement app-owned typed brokers first, starting with BelloCode's native GitLab operations. Keep each secret in Keychain; grant an operation capability scoped to project, account, destination, method/path and expiry, with user-visible approval and revoke. Never inject the value, a reusable credential, or raw remote output into agent shell/MCP environment, files, arguments, events, logs or transcript. The agent receives a status and strictly allowlisted fields. For arbitrary CLI compatibility, research the constrained proxy separately; do not advertise it as equivalent until its enforced network, endpoint, response and side-channel boundaries are verified. Disable or clearly label the current secret-exec/pipe path as **command can reveal secret**, not “hidden from agent.”

Precise claim: **for a brokered operation, the secret value is never supplied to the model or agent-controlled process by BelloCode, provided the broker, OS/VM, Keychain and destination service are trusted, and the operation's permitted outputs do not encode or reflect the value**. This is not a guarantee against a malicious destination, compromised host, pre-existing copies, or information conveyed by permitted results/timing. Treat output filtering as a schema and information-flow design, not a search-and-replace promise. UI shows secret label (never value), project, destination, operation, grant duration and last use; transcript says “Used secret through broker,” with result status and revoke. If no safe broker exists, say unavailable; do not silently downgrade.

## 5. Interrupt another thread

Replace the current same-project `bellocode_interrupt` approval requirement ([orchestration scoping](../features/orchestration.md#scoping-and-safety)) with an attributed same-project action, including unrelated threads, without asking. Verify caller session and canonical project ID server-side; refuse unattributed, stale or deleted targets; cross-project remains an explicit approval. An injected agent can otherwise repeatedly stop valuable work. Rate-limit per caller and target, deduplicate concurrent requests and cap cascades. Show who interrupted whom and why in **both** transcripts and an audit entry, report requested versus acknowledged/actual terminal state, and expose a keyboard-accessible Resume action in the target. Resume is an undo-style continuation, not a true rollback: side effects already made cannot be undone, and queued work stays held until explicitly resumed. Child cascade behavior and a concurrent human stop must remain idempotent.

Validation for implementation: pinned-binary contract tests for permission ordering, saved grants, hook coverage, event loss/reconnect, child sessions and reviewer failure; adversarial prompts and shell indirection; broker canary secrets with reflected/encoded responses, redirects, errors, logs and artifacts; network bypass and DNS tests in the real Rancher environment; interruption attribution, cross-project refusal, rate limits and resume races. Perform the UX acceptance checklist in [research 03 §E](03-ux-patterns.md) when the feature is built. None of these implementation tests or live provider reviews was run for this research.
