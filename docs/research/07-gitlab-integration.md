# GitLab integration research

Research snapshot: 2026-11-16. Target one enterprise, potentially several self-managed hosts. No forge CLI or OAuth. Git, worktrees and local diffs remain with git/opencode; the in-progress MR link/watch service should own one shared GitLab client and watcher. T3's GitHub PR discovery, multiple links, watch and review features ([inventory](04-t3code-feature-inventory.md#12-pull-requests)) are the behavioral baseline. Recommendations below are designs, not claims that this repository implements them.

## 1. Authentication and trust

- Store each access token as a separate macOS Keychain item keyed by normalized HTTPS origin **and installation base path**, account/token identity and purpose; allow several installations and accounts. Use `PRIVATE-TOKEN` on HTTPS requests, never URL query parameters. Do not log authorization headers, trace bodies, token values or git credentials. A configured instance URL such as `https://host/gitlab` produces `https://host/gitlab/api/v4/...` and `/api/graphql`; do not lose the prefix when resolving redirects or remote paths. Reject credential-bearing redirects to another origin or outside the configured installation; request explicit configuration instead. Sources: [REST authentication](https://docs.gitlab.com/api/rest/authentication/), [relative URL installation](https://docs.gitlab.com/install/relative_url/).
- **Personal access token (PAT):** acts as the user, respecting their project membership and permissions; best default for attribution and individual reviews. **Project access token:** project bot identity and role, constrained to project; suitable for one-project automation but review actions appear as the bot and access to other resources can differ with visibility. **Group access token:** group bot and assigned role across group/subgroups/projects; larger blast radius. GitLab.com resource token availability depends on paid tier; self-managed supports them with any license, subject to admin policy. Check instance and role rather than infer access from token scope. [PATs](https://docs.gitlab.com/user/profile/personal_access_tokens/), [project tokens](https://docs.gitlab.com/user/project/settings/project_access_tokens/), [group tokens](https://docs.gitlab.com/user/group/settings/group_access_tokens/).
- **Scopes:** `read_api` for REST/GraphQL reads of projects, MRs, discussions, approvals, pipelines/jobs, issues, users, branches and to-dos, subject to endpoint and project permissions. `api` for mutations: create/update/merge MRs, notes, approvals, to-dos and CI actions; this is broad, not per-operation authorization. `read_repository` is Git-over-HTTPS read and repository-files REST read, not general MR API read; `write_repository` is Git-over-HTTPS read/write, **not API authentication**. `api` also grants Git-over-HTTPS repository access. A read-only token and a separate write token reduce exposure when enterprise policy permits. New granular token scopes and exact endpoint coverage are version-dependent; verify per endpoint, do not presume them. [Token scopes](https://docs.gitlab.com/security/tokens/access_token_scopes/).
- Validate with `GET /user` and a project-specific read; a successful user lookup alone proves neither scope nor access to a particular project. `GET /personal_access_tokens/self` returns metadata such as scopes, expiry, active/revoked state for supported access tokens; verify behavior for each resource token and version, and try resource-specific access-token APIs only with sufficient permission. A 403/404 or missing fields means **unknown**, not “no expiry.” Never enumerate or print tokens. [Token introspection](https://docs.gitlab.com/api/personal_access_tokens/#self-inform).
- Current docs: default maximum lifetime is 365 days, expiry at 00:00 UTC on the expiry date; 17.6 introduced an optional 400-day maximum behind `buffered_token_expiration_limit`, with administrator settings and Ultimate policy potentially imposing a shorter maximum. Older versions, legacy tokens and administrator policy can differ; some installations permit non-expiring PATs. Do not promise a universal limit. Display actual expiry/unknown, warn at e.g. 30, 7 and 1 days and on launch after sleep; persistent banner on expiry and reconnect instructions. [PAT expiration](https://docs.gitlab.com/user/profile/personal_access_tokens/#access-token-expiration).
- Rotation returns the new secret only once and immediately revokes the old token; API rotation requires `api` or `self_rotate` and appropriate version/permissions. Do not silently rotate: interrupted delivery or Keychain failure can lock the user out. Prefer the user creating and validating a replacement before switching; keep the previous credential until successful validation, then remove it. Rotation via `/personal_access_tokens/self/rotate`, `/projects/:id/access_tokens/self/rotate`, or `/groups/:id/access_tokens/self/rotate` must be capability-tested; recovery is manual if the new secret is lost. [PAT API](https://docs.gitlab.com/api/personal_access_tokens/), [project token API](https://docs.gitlab.com/api/project_access_tokens/), [group token API](https://docs.gitlab.com/api/group_access_tokens/).
- Use macOS system certificate evaluation and system proxy configuration (including enterprise CA, PAC and authenticated proxy as supported by URLSession); never disable TLS verification. Show hostname, certificate/proxy failure and remediation without secrets. Git uses its own TLS/proxy configuration and may not share URLSession trust; test the installed git and enterprise CA setup separately. No arbitrary proxy bypass or credential forwarding to proxy/redirect hosts.
- **Git transport:** default to user's existing credential helper or SSH agent/config, and offer app-managed HTTPS only as an explicit opt-in. For app-owned git invocations, a narrowly scoped credential helper can read the host/path-matched Keychain item, pass it on git's credential protocol stdin/stdout, and use `credential.useHttpPath` where needed; `GIT_ASKPASS` is an alternative with a controlled executable, never the token in its environment or arguments. Never put a token in remotes, repo config, command arguments, logs or model messages. For agent-run arbitrary shell/git, an agent can invoke a helper or exfiltrate any credential it can access; a helper is **not a secrecy boundary against a malicious process**. Stronger default: app brokers approved fetch/push itself with short-lived, narrowly scoped credentials and does not expose the credential facility to the agent environment. SSH is the alternative, but agent-accessible SSH agents also confer signing authority. [Git credentials](https://git-scm.com/docs/gitcredentials), [GitLab Git HTTPS](https://docs.gitlab.com/user/profile/personal_access_tokens/#use-personal-access-tokens).

## 2. Endpoint map

All paths below are relative to configured `/api/v4`. `P` is numeric project ID or URL-encoded full namespace path; `I` is the **project-local MR IID**, not global ID. `M = /projects/:P/merge_requests/:I`. Encode each path parameter once, including `/` in project names, and preserve case. Follow pagination links; don't guess numeric IDs. Access, roles, edition and server version still govern every operation. GitLab's [REST conventions](https://docs.gitlab.com/api/rest/) and [GraphQL reference](https://docs.gitlab.com/api/graphql/reference/) are authoritative.

| Operation | REST path, parameters and gotchas |
| --- | --- |
| Resolve remote | `GET /projects/:P` ([projects](https://docs.gitlab.com/api/projects/#retrieve-a-project)). Parse HTTPS/SSH/scp-style host, port and nested namespace; remove terminal `.git`; match a configured installation including path prefix. SSH URL may not reveal the web prefix: ask for mapping. Fork source and target may differ; confirm project identity and persist numeric ID. GitLab can hide inaccessible projects with 404. |
| Find/read MR | `GET /projects/:P/merge_requests?state=opened&source_branch=...` and `GET M`; include source project identity for forks and allow multiple matches. `updated_after` applies to list, not a universal change stream. `diff_refs` can initially be empty due to asynchronous preparation; `detailed_merge_status` evolves asynchronously. [MR API](https://docs.gitlab.com/api/merge_requests/). |
| Create/edit | `POST /projects/:P/merge_requests` with `source_branch`, `target_branch`, `title`, optional `target_project_id`, `description`, `assignee_ids[]`, `reviewer_ids[]`, `labels`; `PUT M` with changed fields and `state_event=close|reopen`. Draft uses `Draft:` title convention; do not assume a writable `draft` boolean. Verify permissions and fork source/target. |
| Merge/rebase | `PUT M/merge` with reviewed `sha`, optional `auto_merge=true`; older versions use `merge_when_pipeline_succeeds` (deprecated 17.11). GitLab applies all checks, policy and protected-branch rules; detect 405/409 and re-fetch. `PUT M/rebase` queues work; inspect `rebase_in_progress` and error fields, do not claim immediate completion. |
| Approvals | `GET M/approvals`, `GET M/approval_state`, `GET M/approval_rules`; `POST M/approve` with `sha`, `POST M/unapprove`. Free allows optional approvals; required approval rules and enforcement are Premium/Ultimate. Approvers, resets, hidden groups, reauthentication and project policies can constrain or mask details. [Approval API](https://docs.gitlab.com/api/merge_request_approvals/). |
| Discussions | `GET/POST M/discussions`; `GET/PUT M/discussions/:discussion_id` (`resolved=true|false` where resolvable); `POST M/discussions/:discussion_id/notes` (`body`). Paginate; not all notes are resolvable. [Discussions](https://docs.gitlab.com/api/discussions/). |
| Notes and suggestions | `GET/POST M/notes`, `PUT M/notes/:note_id` (`body`); list supports `sort`, `order_by`, not a documented universal `updated_after`. General notes and discussions overlap: deduplicate by note ID. Suggestions use GitLab Markdown suggestion syntax inside a diff note; applying them has server-specific constraints, do not treat as local patch without review. [Notes](https://docs.gitlab.com/api/notes/), [suggestions](https://docs.gitlab.com/user/project/merge_requests/reviews/suggestions/). |
| Inline positions | `POST M/discussions` with `body`, `position[position_type]=text`, `position[base_sha]`, `position[start_sha]`, `position[head_sha]`, `position[old_path]`, `position[new_path]`, and `old_line` and/or `new_line` according to change type; ranges need `line_range`. Fetch the exact version first; renamed files need both paths. Stale/outdated, truncated, binary and absent diff lines require explicit fallback, never invent an anchor. [Position rules](https://docs.gitlab.com/api/discussions/#create-a-new-thread-in-the-merge-request-diff). |
| Draft review | GitLab supports draft review comments and publishing; their API is version/tier sensitive. GraphQL `draftNoteCreate`, `draftNotePublish`, `draftNoteBulkPublish` and related schema fields need introspection and compatibility verification on the target instance. Otherwise save a clearly local draft and publish individually; do not imply atomic review submission. [GraphQL reference](https://docs.gitlab.com/api/graphql/reference/), [reviews](https://docs.gitlab.com/user/project/merge_requests/reviews/). |
| Diffs/versions | `GET M/diffs` paginated; `GET M/versions` and `GET M/versions/:version_id` return `base_commit_sha`, `start_commit_sha`, `head_commit_sha` and changes. `GET M/changes` is deprecated for API v5; limit/overflow and `collapsed`/`too_large` fields depend on version. Avoid presenting missing diff content as complete. [MR diffs](https://docs.gitlab.com/api/merge_requests/#list-merge-request-diffs). |
| Pipelines | `GET M/pipelines`; `GET /projects/:P/pipelines/:pipeline_id`, `/projects/:P/pipelines?ref=...&updated_after=...`. MR pipelines, branch pipelines, merged-results pipelines and child pipelines differ; bind status to the actual MR pipeline and SHA. Child pipelines may require `source=parent_pipeline` or bridge traversal. [Pipelines](https://docs.gitlab.com/api/pipelines/), [downstream pipelines](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/). |
| Jobs/logs | `GET /projects/:P/pipelines/:pipeline_id/jobs?include_retried=true` includes `stage`, status and job ID; list stages by grouping jobs, preserving server ordering. `GET /projects/:P/jobs/:job_id/trace` returns plaintext, potentially huge or expired. HTTP `Range`/206 support is **unverified** across GitLab, proxies and versions: probe, cap bytes, and handle 200/full response and 416; do not assume efficient server-side tailing. `POST /projects/:P/jobs/:job_id/retry`, `/cancel`, `/play`; play can run deployment jobs. [Jobs](https://docs.gitlab.com/api/jobs/). |
| Downstream | `GET /projects/:P/pipelines/:pipeline_id/bridges` returns trigger jobs and downstream pipeline references; target project permissions may differ. Newer docs introduce `/trigger_jobs` in 19.2 and deprecate `/bridges`; use version-aware fallback. [Jobs API](https://docs.gitlab.com/api/jobs/#list-all-trigger-jobs-by-pipeline). |
| Commit status | `GET /projects/:P/repository/commits/:sha/statuses` (`ref`, `pipeline_id`, `all`, `order_by`, `sort` as supported). External commit statuses and pipeline jobs are not equivalent; identify context, SHA and pipeline. [Commits](https://docs.gitlab.com/api/commits/). |
| Branches/protection | `GET /projects/:P/repository/branches?search=...`, `GET /projects/:P/repository/branches/:branch`; `GET /projects/:P/protected_branches` and `/:name`. Encode branch slashes; wildcard protections can overlap and effective permissions may be more complex than one row. [Branches](https://docs.gitlab.com/api/branches/), [protected branches](https://docs.gitlab.com/api/protected_branches/). |
| Issues | `GET /projects/:P/issues?state=opened&search=...`, `GET /projects/:P/issues/:issue_iid`; `GET /projects/:P/issues/:issue_iid/related_merge_requests` where available. Cross-project links require permission; a description's `Closes` reference is only effective under GitLab's closing rules. [Issues](https://docs.gitlab.com/api/issues/). |
| To-dos/users | `GET /todos?state=pending`, `POST /todos/:id/mark_as_done`; `GET /user`, `GET /users?search=...`, `GET /projects/:P/users?search=...` where supported. A to-do is account-specific; bot-token inbox is the bot's. Large user searches have pagination and visibility constraints. [To-dos](https://docs.gitlab.com/api/todos/), [users](https://docs.gitlab.com/api/users/). |
| Code owners | Read candidate `CODEOWNERS` through `GET /projects/:P/repository/files/:file_path?ref=...`; GitLab's location precedence, inheritance and eligibility matter. Prefer server-computed `M/approval_state` and rules over reimplementing ownership. Required Code Owner approval for protected branches is Premium/Ultimate; basic ownership visibility depends on version. [Code Owners](https://docs.gitlab.com/user/project/codeowners/). |
| GraphQL | `POST /api/graphql` (relative to installation root, **not** `/api/v4`) can request a project, MR, pipelines, approval and discussion fields together with cursor pagination. Introspect schema and handle partial `errors` alongside `data`, cost/depth/rate limits and per-field permissions. Field availability, drafts and subscription support must be checked on the actual version. REST remains fallback. [GraphQL](https://docs.gitlab.com/api/graphql/). |

## 3. Change detection and watch semantics

- One shared scheduler per installation, coalesced by `(host, project ID, MR IID)` across threads/windows; bounded concurrency, request budget, jitter and cached snapshots. Poll actively watched/running MRs about every 60–120 seconds, visible panels about 30–60 seconds, inactive linked MRs every 5–15 minutes; back off when offline, on battery/idle and in background. Manual refresh bypasses normal interval but not 429 backoff. Paused app means no reliable wake until restart unless an explicitly designed background service is running.
- GitLab does **not** document blanket conditional GET/ETag support for all REST endpoints. Send `If-None-Match` only for a representation that actually returned an ETag and honor 304 if observed; key by URL, query and authorization identity. A proxy may supply an ETag; verify correctness. No assumption that 304 is free of rate-limit accounting, or that notes/discussions, approvals, pipeline status and paginated lists provide useful validators. If absent or unreliable, compare bounded canonical snapshots. [REST API](https://docs.gitlab.com/api/rest/), [HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching).
- MR list `updated_after` and pipeline list `updated_after` are optimization hints, with overlap and ID deduplication; never assume every note, approval or job status change advances MR `updated_at`. For each actively watched MR independently refresh MR state, relevant pipeline, approval state and paginated discussions/notes. Follow `Link` headers; use keyset only on endpoints and orderings GitLab documents, otherwise offset pagination with stable ordering, overlap and periodic full reconciliation. Paginated data can move during a scan; cap work and surface stale/incomplete state, then retry. [Pagination](https://docs.gitlab.com/api/rest/#pagination).
- Persist a baseline and a transactional outbox with watch generation and event keys: `(host, project, MR, pipeline ID, terminal status)`, `(MR, note ID)` and `(MR, approval snapshot revision/hash)`, `(MR, state, transition identity)`. After an initial baseline, enqueue once per observed transition and mark delivered only after the thread accepts it; restart safely replays unacknowledged deliveries. Coalesce bursts, exclude own/system notes by policy, bound queues and visibly resync on overflow. Cancel generations when unwatching. MR merge/close ends watch after delivery unless reopened and explicitly rewatched.
- Guarantees are **once per durably observed event**, not exactly once per real-world transition: polling can miss an approval added and removed, a note created and deleted, a fast intermediate pipeline state, or an MR merged and reopened between polls; snapshots cannot reconstruct those events. Reconcile on reconnect, handle edited/deleted notes, pipeline retries/new IDs, SHA changes, permission changes and manual jobs (`manual`/`blocked` is not successful completion). Show last successful refresh and a gap/stale indicator; never claim no activity during a gap. A review comment is a new non-system note identified by ID; approval changes are set differences with attribution only when returned. Fetch failing job excerpts on demand with bounds and SHA/pipeline context.
- Honor `Retry-After` (seconds or date) and available `RateLimit-*` headers; on 429 stop host-wide work until reset with jitter, exponential backoff if absent, and expose throttled/stale state. Limits differ between GitLab.com and self-managed, may be configured by admins or proxies, and some endpoint-specific limits aren't reflected in headers. Do not hardcode GitLab.com limits for the enterprise. [Rate limits](https://docs.gitlab.com/administration/settings/user_and_ip_rate_limits/), [REST limits](https://docs.gitlab.com/security/rate_limits/).
- GraphQL subscriptions use GitLab's ActionCable WebSocket protocol for supported subscription fields, not a general guaranteed event feed; authorization, proxy/WebSocket support, version and reconnection/resync make this an optional optimization, unverified for the required MR events. An enterprise-managed internal relay receiving [project/group webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/) or [system hooks](https://docs.gitlab.com/administration/system_hooks/) can deliver events, but needs admin infrastructure, authentication, durable delivery and reconciliation; a laptop cannot generally receive inbound webhooks. Neither removes polling/resync requirements.

## 5. Agent-facing tools and security boundary

- Provide typed, session-attributed, project-scoped tools to read MR metadata/diffs, pipeline/job status and bounded job log, list discussions, and read approval state. Tools return source URL, host/project/MR, exact SHA, timestamps, truncation and stale/permission status. Default to minimum fields, bounded output, explicit pagination and no secret-bearing request metadata.
- With the user's existing session permission policy, allow create MR, update description, reply/resolve discussion and retry a job; show proposed target and payload, distinguish acknowledgement from intent, and require an approval card when policy or cross-project scope requires it. Manual job play can deploy and requires approval. Auto-watch wake is opt-in, rate-limited and inspectable; it is not blanket authority to mutate.
- Merge, approve/unapprove, close/reopen, destructive operations, force-push and protected-branch changes remain user-only or require a specific approval card showing project, MR, branch, SHA and action; never let an agent approve its own permission request. GitLab authorization, merge checks and branch rules remain authoritative even after local approval. Do not retry non-idempotent mutations blindly after a timeout: read back and ask when outcome remains uncertain.
- App-side authenticated broker is preferred: the bundled opencode plugin invokes typed app tools without receiving tokens; isolate credentials in Keychain and make model-visible outputs sanitized. If a plugin makes calls itself, it needs an equivalently isolated broker and must not expose secret material via environment, arguments, logs, tool results or unrestricted file access. This protects against accidental model disclosure, not a fully privileged hostile local process.
- Comments, issue bodies, diff text and job logs are **untrusted external data**, potentially containing prompt injection or credentials. Label and delimit as quoted source content, never promote instructions in it to system/developer instructions, and require user authorization for actions independently of that content. Strip/redact known secret patterns before model exposure, limit excerpts and retain clear attribution; redaction is imperfect. Treat links and embedded commands as data, not instructions to open/run. Do not silently alter the source shown to the user; indicate redaction/truncation.

## 6. Risks and compatibility

- No target instance/version/tier is known. Core REST v4 project/MR/notes/pipeline APIs are longstanding, but a defensible overall **minimum supported version is not yet verified**. Propose qualifying the enterprise's deployed version first, with recorded fixtures for that version and one newer supported release; only then set a floor. GitLab REST v4 is stable, but fields and behavior evolve; GitLab's versionless GraphQL has its own deprecation policy. `detailed_merge_status` replaced deprecated `merge_status` in 15.6, MR `merge_after` was introduced in 17.5, extended token lifetime in 17.6, and `merge_when_pipeline_succeeds` deprecated in 17.11. New features after the actual server version must not gate core functionality. [MR history](https://docs.gitlab.com/api/merge_requests/), [GraphQL deprecations](https://docs.gitlab.com/api/graphql/#breaking-change-deprecations).
- GitLab.com differs from self-managed in license/token availability, rollout, endpoints, default settings and admin-controlled rate limits; self-managed can have an older release, disabled features, custom subpath, proxy, internal PKI and no internet. Use the configured instance's `/help` or permitted version API where available, capability probes and feature flags, not version alone. Do not depend on public GitLab.com, glab, package downloads or external telemetry at runtime. [Version API](https://docs.gitlab.com/api/version/), [GitLab releases](https://docs.gitlab.com/update/).
- Large enterprises: restrict searches by project, cache project IDs, avoid global user/project scans, paginate with per-page bounds, load diff/log content lazily, limit parallelism, avoid repeated full history and account for response truncation and GitLab's offset limits. Don't rely on totals being returned on large collections. Rate-limit retries and background work together.
- Explain 401 as expired/revoked/invalid credential, 403 as insufficient role/scope/policy, 404 as missing **or hidden**, 409/405 as changed state or rejected operation, 429 as throttled, and network/TLS failures separately; do not claim certainty from status alone. Preserve cached data with timestamp, never show an empty result as authoritative after an error. Project, branch, MR and requested action belong in the error, not secrets.
- Unverified on a real enterprise GitLab: endpoint behavior for ETags and byte ranges, GraphQL review drafts/subscriptions, token introspection for each resource-token type, custom CA/proxy and git credential behavior, edition/role distinctions and exact minimum versions. Contract fixtures and a real-instance acceptance pass are required before shipping.

## Recommended build order and owner decisions

1. Harden the in-progress link/watch with multi-host Keychain auth, project resolution, bounded polling, durable baseline/outbox, stale states and versioned integration fixtures. Preserve git's existing transport by default.
2. Add sidebar/header MR chips, MR panel, pipeline/job details and bounded failure triage; then editable MR creation and issue-to-thread.
3. Add version-anchored inline review and discussion actions; next add approval/code-owner awareness, to-dos, and optional dependent-MR visualization. Gate agent mutation and merge controls explicitly.
4. Qualify real self-managed versions, tiers, TLS/proxy and failure behavior; test reconnect, rate limits, race conditions and human review before enabling automatic wakes broadly.

| Owner decision | Default assumption until answered |
| --- | --- |
| Deployed GitLab version and tier, upgrade policy? | Self-managed Free; minimum unknown, capability-gate and verify against the deployed release. |
| Hostname(s), installation path(s), proxy and CA? | One HTTPS self-managed installation, possibly with a path prefix and enterprise system-trusted CA; permit more than one. |
| Allowed token type, roles, scopes and rotation policy? | Per-user PAT, `read_api` for reads; request `api` only for explicitly enabled writes. Keychain storage; no OAuth. |
| Git transport: HTTPS or SSH, managed credentials? | Keep the user's existing git/SSH setup; do not expose the API token to agent shells. |
| Approve or merge from BelloCode? | No agent authority; user-only controls disabled until explicitly wanted, with SHA checks if enabled. |
