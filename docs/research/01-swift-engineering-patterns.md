# Swift engineering patterns for BelloCode

Research date: 2026-11-16. Scope: macOS 15+, Apple Silicon; a local OpenCode server and a long-lived, streaming coding workspace. Rankings are by expected product impact, not by frequency across all Mac apps. **High** means directly supported platform behavior or a robust design principle; **medium** means an informed architectural choice that needs a BelloCode prototype; **low/unverified** marks assumptions or missing evidence. No BelloCode benchmark was run. The public OpenCode server documentation consulted is explicitly **V1**; it does not verify the supplied v2 binary's behavior.

“Native” does not automatically produce a good Mac app. Main-thread work, a poorly bounded update graph, incorrect identity and scroll ownership, and failure to use the responder system can make native controls feel worse than a well-engineered cross-platform application. Apple describes SwiftUI performance in terms of dependencies, update frequency and identity, rather than claiming a particular framework is universally fast ([WWDC23: Demystify SwiftUI performance](https://developer.apple.com/videos/play/wwdc2023/10160/); [WWDC21: Demystify SwiftUI](https://developer.apple.com/videos/play/wwdc2021/10022/)). The source material does **not** establish that most Swift apps are bad or that all the issues below are current macOS 15 bugs.

## A. Ranked anti-patterns

### 1. Treat every token as a new transcript

- **Symptom:** typing, scrolling and window resizing hitch during generation; CPU rises with conversation length; scroll position jumps.
- **Cause:** publishing 50–200 mutations per second into a shared root model, reparsing the complete Markdown, rebuilding identities or measuring all rows for every delta multiplies update, text-layout and drawing work. `@Observable` tracks properties read by a view; `ObservableObject` typically invalidates observers on object-level change. Neither makes an expensive computed property or a frequently read root property free.
- **Evidence:** Apple's [Observation session](https://developer.apple.com/videos/play/wwdc2023/10149/) explains property-access tracking; [SwiftUI performance](https://developer.apple.com/videos/play/wwdc2023/10160/) discusses dependency scope and list identity. These sources explain the mechanism, not a measured 50–200 Hz BelloCode result.
- **Fix:** stable per-message IDs and narrow per-message state; append ordered deltas to an actor-owned buffer, then publish a merged snapshot at an initial 30 Hz maximum (33 ms), flushing immediately at completion/error. Parse only the changed active message, cache finalized messages, and batch main-actor commits. **30 Hz is a starting hypothesis**, test 16–50 ms against latency, CPU and accessibility. Never drop semantic deltas; dropping intermediate *render snapshots* is fine. **Confidence: high** for scoping/coalescing; **medium** for the numerical cadence.

### 2. Assume a lazy stack is a transcript engine

- **Symptom:** long heterogeneous messages or tool cards stutter during scroll; prepend/load-more changes the viewport; an offscreen item's changing height causes apparent jumps; virtualized rows lose local state.
- **Cause:** lazy construction does not remove the costs of identification, diffing, measuring dynamic heights, attributed text or view lifetime. SwiftUI scroll APIs exist, but a chat additionally needs explicit rules for bottom-follow, preserved viewport and changed heights. Behavior depends on OS release and layout; no source here proves a universal row-count threshold.
- **Evidence:** Apple's [SwiftUI performance session](https://developer.apple.com/videos/play/wwdc2023/10160/) describes list identity and efficient updates; Apple's [Beyond scroll views](https://developer.apple.com/videos/play/wwdc2023/10159/) presents scroll positioning tools. They do not benchmark this heterogeneous workload.
- **Fix:** prototype SwiftUI `List` and `ScrollView`/`LazyVStack` on macOS 15 and the actual dev OS with 1,000–10,000 mixed rows, streaming, resize, prepends and large code blocks. Start with an AppKit `NSCollectionView`/`NSScrollView` controller for the production transcript if anchor, selection or measured latency gates fail. Reuse item views, use stable message IDs and cache heights by content revision + width + typography; invalidate only affected entries. Record the top visible ID and its offset before prepend/relayout; restore after layout. Bottom-follow only if the user was already within a measured bottom threshold; offer “jump to latest.” Beware async image loads and a single huge message: row virtualization alone does not bound their text layout. **Confidence: medium** for the specific control; high for explicit anchoring and measurement.

### 3. Fragment a selectable document into independent views

- **Symptom:** selection stops at a message or code block, Copy misses intervening text, selection disappears on updates, keyboard navigation feels unlike a Mac text view.
- **Cause:** each text view owns its own selection; `.textSelection(.enabled)` enables selection but does not by itself specify one unified selection model across arbitrary separate views. Row reuse further complicates selection.
- **Evidence:** Apple documents [textSelection](https://developer.apple.com/documentation/swiftui/view/textselection(_:)) and [NSTextView](https://developer.apple.com/documentation/appkit/nstextview); the cross-row consequence is an architectural inference, not an Apple claim that SwiftUI cannot ever implement it.
- **Fix:** decide product semantics up front. If seamless drag selection across messages is a must, prototype a single AppKit text system/document with attachments and virtualization trade-offs, or implement a deliberate transcript-level selection model with accessible copy semantics. If per-message selection suffices, bridge selectable `NSTextView` per message and provide Copy Message/Code actions. Do not claim cross-message selection until tested, including dragging through cards and offscreen content. **Confidence: high** for selection ownership; **medium** for chosen implementation.

### 4. Recreate Mac responder, menu and window behavior with gestures

- **Symptom:** Cmd-C/V, Undo, menu validation, IME composition or focus breaks after pane changes; keyboard shortcuts collide with terminal input; sidebar widths and toolbar controls behave inconsistently; drag targets and contextual actions fail intermittently.
- **Cause:** a Mac has a responder chain, key and main windows, first responder, menu validation and native drag sessions. Generic gesture handlers and duplicated focus state bypass these contracts. `NSViewRepresentable` can also feed delegate callbacks back into state and trigger update loops if ownership is unclear.
- **Evidence:** Apple's [responder chain](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/EventOverview/EventArchitecture/EventArchitecture.html), [SwiftUI focus](https://developer.apple.com/documentation/swiftui/focus), [NSViewRepresentable](https://developer.apple.com/documentation/swiftui/nsviewrepresentable) and [NSDraggingDestination](https://developer.apple.com/documentation/appkit/nsdraggingdestination) describe the relevant APIs. These are failure risks, not blanket claims that SwiftUI controls are broken.
- **Fix by surface:**
  - **Focus and composer:** SwiftUI `@FocusState` for simple controls; bridge `NSTextView` and `window.makeFirstResponder` when multiline editing, IME, selection, undo or reliable programmatic focus demands it. Never steal focus on every stream update. Record intended focus per window and restore only on user navigation or pane dismissal.
  - **Menus and shortcuts:** standard SwiftUI `Commands`/menu items and focused values for simple actions; AppKit target/action, responder chain and `validateMenuItem` for first-responder-specific Edit actions and terminal routing. Test conflicting shortcuts and system-reserved combinations.
  - **Sidebar/splits:** start `NavigationSplitView` for ordinary navigation; use `NSSplitViewController` when persistent divider positions, minimum sizes, precise collapse semantics or restoration require control. Persist semantic state and test window resize/full screen; do not assume an OS-independent SwiftUI bug.
  - **Window/toolbar/titlebar:** standard SwiftUI scene/toolbar for normal Mac behavior; use `NSWindow`/`NSToolbar` via a window controller if native tabbing, titlebar accessories, toolbar customization or restoration cannot be expressed reliably. Avoid global window lookup; retain per-window ownership.
  - **Drag/drop and context menus:** SwiftUI `draggable`/`dropDestination` and `.contextMenu` for simple data and menus; use AppKit pasteboard/drag destination or `NSMenu` delegate for file promises, validation, location-sensitive actions and interoperability when needed. Test Finder, external apps, dragging out and cancellation.
  - **Bridges:** coordinator owns delegates; create the native object once, make updates idempotent, reconcile only changed values, remove observers on teardown and break retain cycles. **Confidence: high** for responder and bridge principles; **medium** for each framework boundary until tested.

### 5. Put async work on the main actor and call it background work

- **Symptom:** typing pauses despite `Task {}`; Swift 6 diagnostics lead to unsafe annotations; intermittent stale UI or crashes on cancel/switch session.
- **Cause:** an unstructured task inherits actor isolation; an `async` function is not a promise of a background thread. CPU-heavy Markdown, syntax highlighting, JSON decoding, image processing or synchronous file I/O can still monopolize the main actor. Actors serialize their mutable state but are reentrant across `await`; unstructured tasks outlive views unless explicitly cancelled. Swift language/toolchain isolation defaults and feature flags change exact behavior.
- **Evidence:** [Swift concurrency](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/concurrency/), [Swift 6 migration guide](https://www.swift.org/migration/), and [Swift evolution: execution of non-actor-isolated async functions](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0338-clarify-execution-non-actor-async.md). Consult the enabled Swift 6.4 language settings; do not extrapolate SE-0338 as the only possible configuration.
- **Fix:** isolate UI state and AppKit to `@MainActor`, own networking/parser/persistence state in appropriate actors, and use explicit, structured off-main CPU work with immutable `Sendable` input/output. No AppKit views cross actors. Check cancellation and a session/generation ID before committing results; serialize ordering-sensitive operations. Do not use `@unchecked Sendable` merely to silence errors, and do not use `Task.detached` as a general escape hatch. **Confidence: high**.

### 6. Confuse an `AsyncStream` buffer with backpressure

- **Symptom:** memory grows after a slow UI falls behind; a bounded stream silently loses tokens; cancellation leaves a network request running.
- **Cause:** `AsyncStream.Continuation.yield` is synchronous and buffering policies control retention/dropping; the producer is not automatically suspended until the consumer catches up. Default unbounded buffering can accumulate indefinitely. An async sequence consuming URLSession bytes is useful, but does not define an application-level memory budget.
- **Evidence:** [SE-0314 AsyncStream](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0314-async-stream.md) documents buffering, yield and termination; [URLSession bytes](https://developer.apple.com/documentation/foundation/urlsession/bytes(for:delegate:)) exposes asynchronous bytes.
- **Fix:** use a bounded, ordered processing pipeline. Coalesce adjacent textual deltas by message into a bounded accumulator while preserving all bytes and event ordering; never replace an arbitrary queue of semantic events with `bufferingNewest(1)`. Put a hard memory limit on pending data; if exceeded, cancel and reconcile with authoritative state, or use a producer-suspending channel where the producer can genuinely await. On termination cancel the URLSession task, flush only valid work, and clean up continuations. **Confidence: high**.

### 7. Design the server as a fire-and-forget `Process`

- **Symptom:** two windows connect to the wrong service, startup races readiness, an exited child is reported as healthy, pipe buffers deadlock, stale servers survive crashes, sleep/wake leaves a false connected indicator.
- **Cause:** launching a PID is not readiness or identity; reserving a free port then closing it before the child binds is a time-of-check/time-of-use race; a PID file alone risks PID reuse. Environment and inherited file descriptors matter. App termination callbacks are not guaranteed after SIGKILL or a crash.
- **Evidence:** the public [OpenCode server documentation](https://opencode.ai/docs/server/) is labeled **V1**: it documents `opencode serve`, loopback default `127.0.0.1`, port default 4096, `/global/health`, SSE, and optional basic authentication. None of these is verified for v2. Apple's [Process](https://developer.apple.com/documentation/foundation/process) describes child process management.
- **Fix:** a single supervisor actor with states stopped/starting/healthy/reconnecting/stopping/failed; launch an explicitly resolved bundle executable with controlled environment and bounded, continuously drained stdout/stderr; monitor exit and health, verify expected service identity/version and use jittered capped restart with a visible failure state. Prefer server-supported bind-to-port-zero plus reported actual port, inherited listening socket, or another atomic server-supported mechanism; otherwise retry failed binds and authenticate the endpoint. Restrict listener to loopback and use server-supported authentication; loopback alone does not identify a local client. On normal quit terminate, wait a bounded time, then escalate only for the verified owned child; handle wake with health check and reconnect. Investigate process groups and orphan strategy for the actual binary; never blindly kill a stale PID. Avoid multiple supervisors per intended server. **Confidence: high** for lifecycle needs; exact v2 mechanics **unverified**.

### 8. Parse SSE as lines of JSON and assume reconnect means replay

- **Symptom:** missing/malformed events after split UTF-8 characters, multi-line data, heartbeat comments or reconnect; duplicated tools or an apparently complete transcript with a gap.
- **Cause:** SSE is a UTF-8 event framing protocol, not one JSON document per received network chunk or line. Event ID and retry fields have stateful semantics. Reconnection is not replay unless the server supports retained IDs and `Last-Event-ID`.
- **Evidence:** the normative [WHATWG event stream specification](https://html.spec.whatwg.org/multipage/server-sent-events.html) defines BOM, CR/LF/CRLF lines, blank-line dispatch, multiple `data` lines, comments, `id`, `event`, `retry` and reconnection; OpenCode V1 docs identify an SSE endpoint but do not establish v2 replay.
- **Fix:** use `URLSession.bytes(for:)` as transport and a tested incremental SSE parser or a vetted library; a byte iterator is not an SSE parser. Handle UTF-8 across chunks, field/value splitting, line endings, comments, empty `id` reset, retry, multiline `data`, end-of-stream behavior and content-type/status errors per the standard. Bound line/event sizes; test arbitrary byte boundaries. Reconnect with jitter, track IDs when supplied, deduplicate only by documented stable event IDs, and reconcile sessions/messages from authoritative HTTP state after any suspected gap. Do not automatically retry non-idempotent commands. **Confidence: high** for SSE; actual v2 event semantics **unverified**.

### 9. Pick persistence from a demo and let it become the source of truth

- **Symptom:** a schema change breaks existing installs, a query stalls UI, large transcripts consume memory, a crash leaves a half-updated cache, or cached session state disagrees with the server.
- **Cause:** persisted models, migrations, large relationships, autosave and live query invalidation have costs that are workload- and version-dependent. SwiftData hides SQL and migration details; specific reports from early releases cannot establish a macOS 15 defect rate. Flat JSON rewrites make partial updates and concurrent access awkward.
- **Evidence:** Apple's [SwiftData documentation](https://developer.apple.com/documentation/swiftdata), [ModelContainer](https://developer.apple.com/documentation/swiftdata/modelcontainer) and [schema migration APIs](https://developer.apple.com/documentation/swiftdata/schemamigrationplan); [GRDB](https://github.com/groue/GRDB.swift) documents SQLite transactions, migrations, concurrency and observation. GRDB is an extra third-party dependency, not a guarantee of better performance.
- **Fix:** OpenCode is authoritative for its sessions unless the v2 contract says otherwise; use GRDB/SQLite for a rebuildable paged local cache, explicit transactions and versioned migrations, and small defaults files for UI preferences. Limit stored content, index actual queries, avoid storing every transient token, test upgrade and restore from a prior release. Store credentials in Keychain. SwiftData remains viable for small simple models, but benchmark migration, relationship faults, writes and UI observation for this workload before adopting. **Confidence: medium** on GRDB as best fit; **unverified** that SwiftData is inadequate in this app.

### 10. Sign only the outer app, or sandbox a shell-driven product without a prototype

- **Symptom:** app works from a terminal but fails after download, Gatekeeper rejects it, helper fails signature/library validation, shell/project tools cannot access expected files, or updates cannot install.
- **Cause:** a `.app` is a structured bundle with nested signed executable code; hardened runtime, entitlements, architecture, team identity, quarantine and notarization all affect distribution. App Sandbox restrictions propagate to child/helper workflows; a user-selected project is not unlimited permission to spawn arbitrary unconfined tools. “It builds with SwiftPM” does not produce a notarized app automatically.
- **Evidence:** Apple's [notarization guidance](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [code signing guide on nested code](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html), [App Sandbox](https://developer.apple.com/documentation/security/app-sandbox), and [Sparkle sandboxing guide](https://sparkle-project.org/documentation/sandboxing/).
- **Fix:** for Developer ID distribution, start with a non-App-Sandboxed hardened-runtime app, since arbitrary project/shell access is core; this deliberately forgoes sandbox confinement and is **not Mac App Store eligible without meeting its rules**. Validate team and license of bundled OpenCode and all nested binaries, dynamic libraries and architectures; sign inside out with appropriate per-component entitlements, sign the app, verify signatures, submit with `notarytool`, staple, and test a quarantined fresh download. Avoid blanket `--deep` signing or disabling library validation without a demonstrated requirement. Secure auto-updates with Sparkle's signed appcasts/EdDSA and a tested update path; framework/helpers must also be signed correctly. **Confidence: high** for signing requirements; sandbox choice **medium**, pending a real entitlement and threat-model test.

### 11. Treat a fast local debug launch as release quality

- **Symptom:** visible beachballs only on large sessions, 120 Hz scrolling feels uneven, memory climbs after repeated sessions, or a GUI test misses a broken keyboard path.
- **Cause:** the main thread shares time with event handling, layout and commits; memory and launch dependencies accumulate in long-lived processes. At 120 Hz a display interval is 8.33 ms, at 60 Hz 16.67 ms; those are whole-frame intervals, **not** guaranteed application CPU budgets. Variable refresh and render-server scheduling complicate interpretation.
- **Evidence:** Apple's [Analyze hitches](https://developer.apple.com/videos/play/wwdc2020/10077/), [SwiftUI Instruments](https://developer.apple.com/videos/play/wwdc2025/306/) and [MetricKit](https://developer.apple.com/documentation/metrickit) describe measurement. The 2025 SwiftUI instrument requires compatible Xcode/Instruments tooling; verify availability on the actual machine. MetricKit delivery and metrics vary by OS, app distribution and configuration; it is not a replacement for local traces.
- **Fix:** use release-like builds and representative fixtures; capture Time Profiler, Hitches/Animation Hitches and SwiftUI instrument where available, Allocations/Leaks and memory graphs. Add `os_signpost` intervals around event receipt, batch publish, parse, layout, database reads, first usable window and server readiness. Measure p50/p95/p99 event-to-visible latency, hitch time/ratio, main-thread work, memory at 10k messages and after repeated session switches, plus cold/warm launch and first input. Record machine, OS, refresh rate, build and data. Cache images, parsed/attributed content and layouts with bounded LRU keyed by message revision, width, font, scale and appearance; invalidate correctly and respond to memory pressure. Keep startup's first window independent of full history and server initialization. Initial targets belong in a benchmark protocol, not claimed Apple requirements. **Confidence: high**.

## B. Ranked patterns to adopt

1. **Own the transcript as a measured subsystem.** Define selection, bottom-follow and stable ID semantics before choosing the control; build a repeatable 1k/10k heterogeneous-row benchmark. Prefer an AppKit collection controller if SwiftUI does not meet those specific gates. Keep full conversation data outside reusable row views. [Apple list performance](https://developer.apple.com/videos/play/wwdc2023/10160/).
2. **One ordered ingestion path; many inexpensive projections.** Network/parser actor → domain actor → bounded ordered coalescer → `@MainActor` per-session/per-message presentation state. Publish a maximum of roughly 30 visual updates/second initially, while preserving every semantic event; ensure final flush. Do not rebuild all history. [Observation](https://developer.apple.com/videos/play/wwdc2023/10149/), [AsyncStream](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0314-async-stream.md).
3. **Give the Mac ownership of Mac interactions.** System menu, responder chain, text editing, split behavior, accessibility, standard selection and undo are functional requirements. Test VoiceOver, Full Keyboard Access, IME, dark mode, high contrast, reduced motion and external drag. SwiftUI where it gives correct native behavior; bridge or use an AppKit controller when it does not.
4. **Implement a supervisor and an explicit synchronization contract.** Endpoint ownership, authentication, readiness, bounded restart, cancellation, wake recovery and gap reconciliation are core product behavior. Validate exact binary version and API before coding. SSE replay is conditional on demonstrated server support.
5. **Keep the main actor short and explicit.** Actor-isolated UI mutation only; parse, decoding, text preparation and database operations outside it using Swift 6-safe `Sendable` values. Check actor reentrancy and stale results; avoid locks across suspension. Use instrument evidence rather than thread-name assumptions.
6. **Cache deliberately, then bound and invalidate it.** Finished Markdown, syntax spans, decoded images and text layout can be cached by immutable content revision and rendering environment; cap cost and evict. Keep SQLite rows/page sizes modest. Zed's [Rope & SumTree](https://zed.dev/blog/zed-decoded-rope-sumtree) explains scalable text data structures; Zed is Rust/GPUI, not evidence about SwiftUI performance. Adopt its principle of incremental data structures only if profiling identifies text scaling as a bottleneck.
7. **Treat release engineering as a feature.** Repeatable CLI build → assemble bundle → sign nested code inside out → sign app → verify → notarize → staple → quarantine/upgrade test. Preserve symbol files for crash analysis. Build a full Sparkle update and rollback/recovery test before release.
8. **Prove regressions with deterministic fixtures.** A mock server should replay partial UTF-8/SSE frames, burst tokens, disconnects, duplicates, malformed responses, restarts and slow consumers. UI tests should cover selection, focus, menus, scroll anchor and window restoration; screenshots supplement rather than replace assertions.

### What shipped applications do and do not prove

[Ghostty](https://github.com/ghostty-org/ghostty) describes a native platform UI and GPU-accelerated terminal. It is not a pure Swift application and does not prove a SwiftUI transcript will perform well. [CodeEdit](https://github.com/CodeEditApp/CodeEdit), [IINA](https://github.com/iina/iina), and [Ice](https://github.com/jordanbaird/Ice) are useful open-source Mac implementation references; none was independently benchmarked here and their product problems are not equivalent to streaming chat. Zed's rope article substantiates a data-structure choice, not a claim that its rendering implementation should be copied into BelloCode. No sufficiently detailed primary engineering postmortem or verifiable performance measurement for the ChatGPT or Claude Mac clients was found in this research; claims about their UI framework, defects or causes would be **unverified**. Public anecdotes about poor native apps are not a substitute for a reproducible trace.

### Acceptance protocol and useful initial budgets

These are **proposed project gates**, not published measurements or platform guarantees. Before optimizing, capture baseline and set actual thresholds from the target hardware and user studies.

- Fixture: 10,000 mixed message/tool rows, code fences, diff blocks, images, 100–200 deltas/s, 30-minute stream; an additional pathological single huge message. Report total message sizes and visible viewport.
- While generating: no dropped semantic events; end-to-end text visibility p95 below 100 ms under normal fixture; stable input and scroll, with measured p95/p99 main-thread and hitch traces. Compare 16, 33 and 50 ms commit intervals. Validate VoiceOver and IME alongside performance.
- Anchor: prepend 100 messages and expand a card above viewport; top visible message remains at the same visual offset within 2 points after layout settles; bottom-follow does not resume until the user requests it or returns to bottom. The 2-point threshold is a proposed test tolerance, not an OS guarantee.
- Memory: capture resident/physical footprint after opening, after the 10k fixture, and after 20 session switches; demonstrate a plateau after cache eviction. Record cold start to first usable window and first usable session, separately from server readiness.
- Reliability: kill server during streaming, restart, force bind conflict, simulate sleep/wake, disconnect/reconnect and missing events; no silent loss or duplicate execution. Repeat with the actual signed, quarantined release bundle.

## D. Rules for implementing agents (paste into AGENTS.md)

1. Preserve stable server message IDs and revisions; never use array index or a fresh UUID as row identity.
2. Keep transcript state outside reusable row views; changing a token must not replace the entire history model.
3. Buffer ordered stream deltas and coalesce UI publication; flush on completion and error without dropping semantic data.
4. Never reparse all historical Markdown for a token; cache completed content and invalidate by content revision.
5. Cap caches and pending event bytes; make overflow a visible recover/reconcile path, never silent data loss.
6. Preserve the visible message and offset when inserting above the viewport; follow the bottom only when the user was already following it.
7. Test cross-message selection explicitly; per-row selectable text is not a unified transcript selection.
8. Keep AppKit and presentation mutations on `@MainActor`; move CPU-heavy parsing, decoding and I/O off it with explicit isolation.
9. Pass immutable `Sendable` values across actors; check cancellation and session generation before applying async results.
10. Own and cancel tasks with their session or window; avoid detached tasks and unchecked sendability as shortcuts.
11. Treat `AsyncStream` buffering as storage policy, not producer backpressure; bound every queue.
12. Parse SSE according to the standard, including chunk boundaries, multiline data and event IDs; test byte-by-byte splits.
13. Assume no replay, port-zero behavior or health endpoint until confirmed against the exact bundled OpenCode version.
14. Reconcile authoritative session state after an event gap; do not retry non-idempotent actions blindly.
15. Supervise the child process, drain its pipes, verify readiness and identity, handle exit and wake, and terminate only verified owned processes.
16. Route Edit commands through the actual first responder; test keyboard, IME, undo and terminal shortcut conflicts.
17. Use SwiftUI for standard UI; bridge AppKit or use a native controller when concrete focus, scroll, split or text requirements demand it.
18. Make representable updates idempotent; own delegates explicitly and tear down observers and callbacks.
19. Keep secrets in Keychain, use loopback binding and authenticate the local service when supported.
20. Version and test SQLite migrations; page large histories and treat local session data as a cache until the v2 contract says otherwise.
21. Profile release-like builds with realistic fixtures; record hardware, OS, refresh rate, p95/p99 latency, hitches and memory.
22. Add signposts for server readiness, first usable window, event-to-publish and expensive rendering work without logging private content.
23. Sign nested executables and frameworks before the outer bundle; verify, notarize, staple and test a quarantined release and update.
24. Cover focus, menus, anchoring, selection, accessibility and resize with UI tests; screenshots alone are insufficient.
25. Document measured regressions and unverified platform/API assumptions rather than presenting framework folklore as fact.

## Testing and headless verification notes

Use `swift test` for parser, supervisor state machine, persistence migrations, identity, reducer/coalescing, and anchor arithmetic; inject clock, transport, process launcher and fixtures. Test the SSE parser against the [WHATWG specification](https://html.spec.whatwg.org/multipage/server-sent-events.html), including event boundaries at every byte and reconnect with and without server replay. UI integration can use `xcodebuild test` and XCTest/XCUI on a logged-in macOS test session; package-only projects may need a generated or checked-in test host/project because SwiftPM alone does not supply an app-hosted UI-testing target. Apple's [XCUIAutomation](https://developer.apple.com/documentation/xcuiautomation) and [XCTest performance tests](https://developer.apple.com/documentation/xctest/performance-tests) describe the tools. Capture deterministic window screenshots for light/dark and fixed size/scale with [swift-snapshot-testing](https://github.com/pointfreeco/swift-snapshot-testing), plus semantic assertions for focus, first responder, selected text, menu validation and viewport; fonts, OS versions and rendering differences make image baselines environment-specific. An agent without the Xcode GUI can build/run CLI tests, inspect structured logs and `xctrace` recordings, and automate a logged-in desktop via accessibility or XCUI; headless CI must provide a GUI session and permission for the particular automation mechanism. This research did not validate this repository's actual GUI automation environment or specific CLI build commands.
