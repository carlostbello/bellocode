# noVNC in a WKWebView (swift run ChromeLiveViewDemo; noVNC 1.3 RFB client from the container's websockify, port
# published on 127.0.0.1:16080 for the spike), macOS 27, 2026-11-18
connect (page load + RFB handshake + first frame), 6 runs: 376, 311, 254, 244, 245, 259 ms
first frame rendered: novnc-in-wkwebview.png (Chromium in the container, fixture toggle.html, 1280x800)
input: 5 runs x (1 key + 1 click) sent from the WKWebView -> page-side counter in Chromium = 505 (5 keys x 100 + 5 clicks):
  every key and click arrived
limits of this session: the login session shows no windows (the shell cannot take screenshots), so WebKit reports the
  page "hidden" (document.visibilityState) and suspends/throttles it between calls: requestAnimationFrame and image
  decoding stop, so noVNC stops applying updates after the first frame and timed/async harness steps stall.
  Disabling occlusion detection or hidden-page suspension through private KVC keys hung the harness; not pursued.
  Latency and frame rate were therefore measured with the same noVNC client in a headless Chromium (liveview-novnc.txt).
  Needs a person at the screen: latency/CPU of the WKWebView pane itself.
