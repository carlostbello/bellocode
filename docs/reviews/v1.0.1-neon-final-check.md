### NF01 — Client-MCP hosts (`bellocode_app` and `bellocode_chrome`) never attach to newly added projects and never reconnect after an opencode server restart

- **Severity:** `blocker`
- **Location:**
  - `Sources/Engine/Presentation/Engine.swift:545-556, 577-581, 594-611`
  - `Sources/Engine/Orchestration/OrchestrationService.swift:276-290`
  - `Sources/Engine/SharedBrowser/SharedBrowserService.swift:350-363`
  - `Sources/OpenCodeKit/Server/ServerSupervisor.swift:132-135`
- **Problem:**
  Two defects combine to leave BelloCode's client-hosted MCP tools (`bellocode_app_*` — scheduled tasks, GitLab MRs/issues/review, secret requests, HTML visuals, container service ports/logs, thread creation/queueing — and `chrome_*` shared browser tools) silently missing for agents:
  1. **Newly added projects while live:** `Engine.connectOrchestration()` is called only on the `!wasLive -> isLive` transition (`Engine.swift:580`). When projects are added or removed while already connected (`applyRoot`, `Engine.swift:594-611`), `Engine` updates `root.projects` and `environments.projectsChanged(...)`, but never calls `orchestration.hostAppTools(...)`, `orchestration.checkPlugin(...)`, or `sharedBrowser.hostTools(...)`.
  2. **Supervised server restarts:** When `ServerSupervisor.restart()` runs (crash recovery, Settings ▸ opencode ▸ Restart Server, or switching the repository-config policy), it spawns opencode on a new random loopback port with a new random password. On reconnect, `connectOrchestration()` calls `orchestration.hostAppTools(directories:)` and `sharedBrowser.hostTools(directories:)`. Both methods skip any already-tracked directory (`for directory in wanted where hosts[directory] == nil`, `OrchestrationService.swift:283` and `SharedBrowserService.swift:357`), leaving existing `ClientMCPHost` instances bound to the dead `WebSocketClientMCPDialer(connection: oldConnection)` looping against the old port/password forever.
- **Failure scenario:**
  - **First-time user:** A new user opens BelloCode for the first time with zero projects. `connectOrchestration()` runs with `directories = []` (skipping `checkPlugin` as well). The user adds or clones their first project and asks the agent to schedule a task, link a GitLab MR, render an HTML visual, request a secret, or use Shared Chrome. None of the `bellocode_app_*` or `chrome_*` tools exist in opencode until the user fully quits and relaunches BelloCode.
  - **Any server restart:** After Settings ▸ opencode ▸ Restart Server, toggling repository-config mode, or recovering from an opencode crash, all previously hosted projects lose every `bellocode_app_*` and `chrome_*` tool for the rest of the app's lifetime.
- **Suggested fix:**
  - Call `orchestration.hostAppTools(directories:)` and `sharedBrowser.hostTools(directories:)` (and `checkPlugin` if not yet checked) whenever `root.projects` changes while `root.connection.isLive` (including overflow snapshot recovery at `Engine.swift:612-624`).
  - Track the `ServerConnection` (or a server generation token) on each `ClientMCPHost` entry in `OrchestrationService` and `SharedBrowserService` (or pass a dynamic connection provider to `WebSocketClientMCPDialer`), and stop/recreate hosts whenever `client.connection` changes on reconnect.
  - Add integration tests covering (a) adding a project after `isLive == true` and (b) restarting/replacing the server endpoint with a new port + credentials and verifying `bellocode_app` and `bellocode_chrome` reconnect.

### NF02 — `ThreadModel.upsert(_:)` silently drops live server message updates on parent messages after sub-agent overlay refreshes

- **Severity:** `blocker`
- **Location:**
  - `Sources/Engine/Presentation/ThreadModel.swift:30, 34-39, 48-55, 515-528`
- **Problem:**
  `MessageModel` keeps two distinct revision concepts: `server.revision` (the revision produced by `ProjectionState` on each server/SSE update) and `message.revision = server.revision + overlayBump` (the rendered revision exposed by `MessageModel.revision` at line 30 so Markdown/row caches invalidate when a sub-agent card changes state). `MessageModel.update(_:force:)` carefully compares `newer.revision > server.revision` (line 35). However, `ThreadModel.upsert(_:)` short-circuits *before* calling `model.update(message)`:
  ```swift
  if let model = models[message.id] {
      guard message.revision > model.revision else { continue }
      model.update(message)
  ```
  Each time a delegated child thread updates its status (e.g., `running` → `awaitingApproval` → `running` → `completed`), `MessageModel.refreshOverlay()` increments `overlayBump` by `+1` (line 51), pushing `model.revision` ahead of `server.revision` by `overlayBump`. Because `ProjectionState` increments the parent message's `server.revision` by `+1` per incoming update, the next `overlayBump` server updates to that parent message satisfy `message.revision <= model.revision` and are dropped at line 520.
- **Failure scenario:**
  A parent agent delegates to a sub-agent. While the sub-agent runs, it triggers an approval/question or completes, bumping `overlayBump` by 2–4. When the parent's `task` tool call finishes (`toolSucceeded`) or emits short follow-up text and completes (`stepEnded`), those `ChangeSet` message updates have `message.revision <= model.revision` and are silently ignored by `ThreadModel.upsert(_:)`. The live transcript displays the parent tool card stuck in "Running" or missing its final text/completion until the thread is closed/reopened or the app restarts.
- **Suggested fix:**
  Remove the premature `guard message.revision > model.revision else { continue }` check at `ThreadModel.swift:520` and delegate the revision check to `MessageModel.update(_:)`:
  ```swift
  guard model.update(message) else { continue }
  ```
  Add a unit test in `EngineTests` that calls `refreshOverlay()` multiple times on a `ThreadModel` parent message and verifies the very next `+1` server revision update (`toolSucceeded` / text delta) is applied and bumps `model.revision`.

### NF04 — Failed first send from a new-thread draft leaves the new thread's composer blank and loses the prompt on the next keystroke

- **Severity:** `major`
- **Location:**
  - `Sources/BelloCodeApp/Content/ComposerSurface.swift:367-369, 430-441`
  - `Sources/BelloCodeApp/Shell/Seams.swift:228-246`
  - `Sources/ComposerKit/Host/ComposerController.swift:81-110, 206-218`
  - `Sources/ComposerKit/Host/ThreadModelComposerHost.swift:261-266`
- **Problem:**
  `DraftComposerHost.send(_:)` intends for a failed first send to restore the prompt into the newly created thread's composer (comment at `ComposerSurface.swift:368-369`). However, the order of operations breaks restoration:
  1. `ComposerController.send()` clears its editor (`applyDraft(.empty)`) and calls `await host.send(submission)` on the draft's `DraftComposerHost` (`ComposerController.swift:202-207`).
  2. `DraftComposerHost.send(_:)` calls `context.createThread(options)` (`ComposerSurface.swift:430`), which immediately invokes `onThreadCreated?(session.id)` (`Seams.swift:240`).
  3. `WorkspaceController` immediately switches selection to `.thread(id)`, tearing down the draft `ComposerController` and mounting a *new* `ComposerController` bound to a *new* `ThreadModelComposerHost` for `model`. That new controller loads `model.draft` (currently `""`) and sets `awaitingDraft = false` once loaded.
  4. Only *after* the UI switch does `DraftComposerHost.send(_:)` call `await host.send(submission)` (`ComposerSurface.swift:439`). If the send fails (offline, rate-limited, provider error, server error), the torn-down draft `ComposerController`'s Task restores the prompt via `host.saveDraft(merged)` (`ComposerController.swift:216`), updating `model.draft`, `ComposerDraftCache`, and `ComposerDraftArchive`.
  5. The live `ComposerController` mounted on screen never reloads `model.draft`: `ThreadModelComposerHost`'s `ObservationTracker` (`ThreadModelComposerHost.swift:261-266`) does not observe `draft`, and `ComposerController.reconcileLoadedDraft()` (`ComposerController.swift:95`) returns immediately whenever `awaitingDraft == false`.
- **Failure scenario:**
  A user types a long prompt with attachments in a new-thread draft and hits Send. Thread creation succeeds, the shell switches to the empty new thread, and the message send fails (e.g., transient server/provider failure or network drop). The user sees an error banner and a completely blank composer. If the user starts retyping or editing, `ComposerController` saves the new text over `model.draft`, permanently destroying the restored original prompt and attachments.
- **Suggested fix:**
  Either (a) defer `onThreadCreated?(session.id)` until after the first `host.send(submission)` returns (or restore the draft onto `model` *before* emitting `onThreadCreated`), or (b) propagate external draft restorations (e.g. via a draft revision counter observed by `ThreadModelComposerHost.ObservationTracker` and reconciled in `ComposerController`) so the mounted thread composer immediately displays a draft written by a failed send. Add a test in `BelloCodeAppTests` / `ComposerKitTests` simulating `createThread` succeeding followed by `send` failing.

### NF05 — Commit & Push (`GitActionsModel.finishCommit`) silently swallows push failures after dismissing the commit popover

- **Severity:** `major`
- **Location:**
  - `Sources/DiffKit/Git/GitActionModels.swift:159-174`
- **Problem:**
  In `GitActionsModel.finishCommit(_:as:)`:
  ```swift
  try await repository.commitAll(message: message)
  commit = nil
  host.notice("Committed to \(repository.status?.branch ?? "HEAD")")
  if action == .commitAndPush || action == .commitPushAndCreateMergeRequest {
      guard try await push() else { return }
      if action == .commitPushAndCreateMergeRequest { host.createMergeRequest() }
  }
  await reload()
  } catch {
      form.error = (error as? GitError)?.userMessage ?? "The commit failed."
  }
  ```
  Line 164 clears `commit = nil`, which dismisses the commit popover and drops `form` from the UI, and line 165 displays `"Committed to <branch>"`. When `try await push()` at line 167 then throws (rejected non-fast-forward, missing upstream/origin, auth failure, offline, hook failure), the `catch` block only assigns `form.error` on the already-dismissed `GitCommitModel` and never sets `lastError` or calls `host.notice(...)`. Even the fallback message says `"The commit failed."` despite the commit having succeeded.
- **Failure scenario:**
  The user chooses **Commit & Push** (or **Commit, Push & Create Merge Request**), writes a commit message, and submits. The commit succeeds locally, the popover closes, and the toast says `"Committed to feature/x"`. The push fails (for example, rejected because remote moved ahead or auth expired). No error appears anywhere in the UI; the user believes their branch was pushed.
- **Suggested fix:**
  Handle `push()` errors separately from `commitAll` errors: once `commit = nil` has dismissed the popover, surface any `push()` error via `lastError` and `host.notice(...)` (or keep the popover open until `push()` settles and show a push-specific error without re-running `commitAll`). Add a unit test in `DiffKitTests` where `commitAll` succeeds and `pushCurrentBranch` throws, asserting that an error is surfaced to `host` / `lastError`.

### NF06 — Settings ▸ opencode "Restart Server…" and Repository Config Policy toggle immediately fail inventory refresh with `.offline`

- **Severity:** `major`
- **Location:**
  - `Sources/Engine/OpenCodeConfig/OpenCodeConfigService.swift:442-453, 463-465`
  - `Sources/Engine/EngineCore.swift:231-235`
  - `Sources/OpenCodeKit/Server/ServerSupervisor.swift:132-135`
  - `Sources/BelloCodeApp/Settings/OpenCodeSettings.swift:253-278`
- **Problem:**
  `ServerSupervisor.restart()` (`ServerSupervisor.swift:132-135`) calls `await stop(); start()` — it returns as soon as the old opencode child stops and the new start task is *scheduled*, while `endpoint` is still `nil`. `EngineCore.restartServer()` (`EngineCore.swift:231-235`) immediately returns `true`, and `OpenCodeConfigService.restart(policy:directory:)` (`OpenCodeConfigService.swift:444-451`) immediately invokes `await refresh(directory: directory)`. Because the new server is not yet ready, `core.currentClient()` throws `EngineError.offline`, setting `refreshError` to an offline error right after every user-initiated restart or repository-config policy switch.
- **Failure scenario:**
  In Settings ▸ opencode, the user clicks **Restart Server…** or toggles **Load every repository's opencode configuration** (`setNative(_:)`). The server begins restarting, and Settings ▸ opencode immediately flips into an error/stale state (`refreshError`) instead of waiting for the restarted server to become ready and refreshing the new agents/commands/skills/plugins inventory. (Combined with NF01, client-MCP tools also fail to reconnect after the restart.)
- **Suggested fix:**
  Have `EngineCore.restartServer()` wait until `ServerSupervisor` reaches `.running` (or `.failed`/`.stopped`, with cancellation support) — or have `OpenCodeConfigService` subscribe to the engine's reconnect notification (`isLive`) to trigger `refresh(directory:)` once the restarted server is actually up. Test `OpenCodeConfigService.restart` against a supervised server lifecycle that goes `.stopped -> .starting -> .running` rather than an always-live mock closure.

### NF14 — Uptime-clock waits (`DispatchSemaphore.wait(timeout: .now() + ...)`) in test helpers bypass `TimerGuardTests`

### NF23 — `SchedulerService.order(_:_:)` violates strict weak ordering on case-only duplicate task names

- **Severity:** `minor`
- **Location:**
  - `Sources/Engine/Extras/SchedulerService.swift:377-379`
- **Problem:**
  ```swift
  private static func order(_ lhs: ScheduledTask, _ rhs: ScheduledTask) -> Bool {
      lhs.name.localizedCaseInsensitiveCompare(rhs.name) == .orderedAscending || (lhs.name == rhs.name && lhs.id < rhs.id)
  }
  ```
  The primary comparison is case-insensitive (`localizedCaseInsensitiveCompare`), while the tie-breaker checks case-sensitive equality (`lhs.name == rhs.name`). Given `C = ("abc", "0")`, `A = ("abc", "2")`, and `B = ("ABC", "1")`: `C` and `B` are incomparable (equivalent), `B` and `A` are incomparable (equivalent), yet `order(C, A) == true`. Equivalence is not transitive, violating Swift `MutableCollection.sort(by:)`'s strict weak ordering requirement.
- **Failure scenario:**
  If a user creates scheduled tasks whose names differ only in capitalization (e.g. `"Daily sync"` and `"daily sync"`), `tasks.sort(by: Self.order)` violates Swift's sort comparator precondition and can produce unstable ordering or trap under IntroSort/TimSort.
- **Suggested fix:**
  Use the case-insensitive comparison result for the tie-breaker:
  ```swift
  let comparison = lhs.name.localizedCaseInsensitiveCompare(rhs.name)
  return comparison == .orderedAscending || (comparison == .orderedSame && lhs.id < rhs.id)
  ```
