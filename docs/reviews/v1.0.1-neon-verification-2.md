## 2. New Blockers and Majors from Q1–Q5 Code Review

No new issues found in Q1, Q2, Q3, or Q4. One **Major** UI/menu wiring defect was found in Q5 (`AF23`):

### `NV2-01` (Major) — Shared Chrome Stop is missing in Settings/panel on `"Stop not confirmed"`, and Stop in `.failed` (Q5 AF23) is unreachable from every UI surface

- **Files:**
  - [Sources/BelloCodeApp/Settings/SharedChromeSettings.swift:27–35, 112–118](../../Sources/BelloCodeApp/Settings/SharedChromeSettings.swift#L27-L35)
  - [Sources/BelloCodeApp/Content/SharedChromeSurface.swift:649–665, 784](../../Sources/BelloCodeApp/Content/SharedChromeSurface.swift#L649-L665)
  - [Sources/Engine/SharedBrowser/BrowserSupervisor.swift:289, 349–361, 406](../../Sources/Engine/SharedBrowser/BrowserSupervisor.swift#L349-L361)
  - [docs/USER-GUIDE.md:378–380](../../docs/USER-GUIDE.md#L378-L380), [docs/RELEASE-NOTES.md:108–109](../../docs/RELEASE-NOTES.md#L108-L109), [docs/features/shared-browser.md:60–61](../../docs/features/shared-browser.md#L60-L61)
- **What happens (two concrete scenarios):**
  1. **Unconfirmed stop (`.stopUnconfirmed`):** Docker returns an error while stopping the shared Chrome container (or while cleaning up after a failed start of an adopted container). `BrowserSupervisor` sets `.stopUnconfirmed("… It may still be running; Stop again to retry.")`. Both `SharedChromeSettingsGroup` (`:114`) and `SharedChromePlaceholder` (`:702`) show that exact instruction, and `docs/USER-GUIDE.md:379–380` explicitly tells the user: *"Choose Stop again (Browser ▸ Stop Shared Chrome or Settings ▸ Browser)"*. Yet `SharedChromeSettingsGroup` (`:27–35`) only renders the **Stop** button when `service.phase.isReady` — in `.stopUnconfirmed` it hides **Stop** and renders only **Start**. `SharedChromePlaceholder` (`:649–665`) also shows `"Stop again to retry."` with no Stop button.
  2. **Stop in `.failed` (new in Q5 `c277c99`) and `.starting` / `.preparingImage` / `.recovering`:** Q5 `c277c99` added `if case .failed = phase` handling to `BrowserSupervisor.stop` (`BrowserSupervisor.swift:349–358`), and both `docs/RELEASE-NOTES.md:109` and `docs/features/shared-browser.md:60` advertise *"Stop in Failed stops one still running"*. However, `SharedChromeMenuRouter.isEnabled(.stop)` (`SharedChromeSurface.swift:784`) only returns `true` for `service.phase.isReady || service.phase.isStopUnconfirmed`, and `SharedChromeSettingsGroup` (`:27`) only shows Stop for `service.phase.isReady`. As a result, **Browser ▸ Stop Shared Chrome**, the **Command Palette**, the **Chrome panel**, and **Settings ▸ Browser** all disable or omit **Stop** in `.failed` (and during `.starting` / `.preparingImage` / `.recovering`). Users have no way to invoke Q5's Stop-in-Failed reconciliation or cancel a stuck start/recovery without quitting the app or disabling Shared Chrome.
- **Why Major:** Violates AGENTS.md UX rules 2 and 8 (failure/recovery actions unreachable from menus and UI), strands a user who follows the app's own `"Stop again to retry"` copy in Settings ▸ Browser, and renders Q5's advertised AF23 Stop-in-Failed fix dead code from the UI.
- **Suggested fix:**
  - Define a single `SharedBrowserPhase.canStop` (true for `.ready`, `.starting`, `.preparingImage`, `.recovering`, `.stopUnconfirmed`, `.failed`) and use it in `SharedChromeMenuRouter.isEnabled(.stop)`, `SharedChromeSettingsGroup` (showing a **Stop** button alongside **Start** in `.stopUnconfirmed`/`.failed`, or **Stop** during `.starting`/`.preparingImage`/`.recovering`), and `SharedChromePlaceholder` (offering **Stop Shared Chrome** in `.stopUnconfirmed` and `.failed`).
  - Add a unit test in `SharedChromeViewerTests` asserting `SharedChromeMenuRouter.isEnabled(.stop, service:)` in `.stopUnconfirmed`, `.failed`, `.starting`, and `.recovering`.

## 3. Documentation Audit — Blockers and Majors

Audited as a new user/developer reading `README.md`, `docs/USER-GUIDE.md`, `docs/RELEASE-NOTES.md`, `CONTRIBUTING.md`, `docs/RELEASE.md`, `Containers/browser/README.md`, and all 21 feature notes in `docs/features/*.md`.

The docs are clear, thorough, and honest about org-specific defaults (`README.md:11–14` matches `docs/PLAN.md` §0). However, four concrete mismatches remain in the front-door docs (`docs/USER-GUIDE.md` and `README.md`):

### `NV2-02` (Major) — Front-door documentation contradicts actual runtime behaviour, menus, and smoke-test commands

1. **Unconfirmed message behaviour is described backwards ([docs/USER-GUIDE.md:383–384](../../docs/USER-GUIDE.md#L383-L384)):**
   - **Doc says:** *"A message shows as unconfirmed. The server did not acknowledge it (for example during a reconnect). Thread ▸ Retry Unconfirmed Message sends it again; the composer keeps the text until the server confirms."*
   - **Code does** ([ThreadModel.swift:241–243](../../Sources/Engine/Presentation/ThreadModel.swift#L241-L243), [UnconfirmedSendsView.swift:6–9, 63–99](../../Sources/BelloCodeApp/Content/UnconfirmedSendsView.swift#L63-L99)): When delivery is unknown, the composer **clears** and deliberately does **not** put the text back into the composer (so the user cannot accidentally send a duplicate under a new ID). Instead, the message is pinned **above the composer** as a `"Delivery unknown"` row with a **Retry** button (matching **Thread ▸ Retry Unconfirmed Message**), which checks opencode first and resends under the same ID only if absent; **Edit in Composer** and **Discard** appear only if Retry confirms opencode never received it.
   - **New-user scenario:** A user disconnects mid-send, sees an empty composer, and thinks their prompt vanished because the troubleshooting guide told them the composer keeps the text.

2. **Browser shortcut scoping rule is inaccurate and stale after Q5 NV05 ([docs/USER-GUIDE.md:347–348](../../docs/USER-GUIDE.md#L347-L348)):**
   - **Doc says:** *"The Browser menu's keys act on the browser that is showing."*
   - **Code does** ([BrowserSurface.swift:348–357, 396–424](../../Sources/BelloCodeApp/Content/BrowserSurface.swift#L348-L357), [SharedChromeSurface.swift:727–736](../../Sources/BelloCodeApp/Content/SharedChromeSurface.swift#L727-L736)):
     - All Browser menu shortcuts except `⌃⌥⌘B` (`Show Shared Chrome`) act **only on the built-in WebKit browser**, never on Shared Chrome (even when the Chrome tab is showing).
     - After Q5 NV05 (`f6bf615`), typed `⌘L`, `⌘R`, `⇧⌘R`, `⌘=`, `⌘-`, `⌘0`, `⇧⌘C`, `⌃⇥`, and `⌃⇧⇥` act on the built-in browser **only when its tab is shown and has focus**; when another view (composer, text field, terminal) has focus while the Browser tab is merely visible, the focused view keeps the key (while `⌃⌘` browser shortcuts stay global and menu clicks still work).

3. **Wrong menu named for `Push` (`⌃⌘P`) ([docs/USER-GUIDE.md:240–241, 334](../../docs/USER-GUIDE.md#L240-L241)):**
   - **Doc says:** Lists **Push (`⌃⌘P`)** under the **Git** menu in both §11 (*"Git menu: … Push (⌃⌘P)"*) and the §16 shortcut table (`Git | Pull / Fetch / Push | ⌃⌘L / ⌃⌘R / ⌃⌘P`).
   - **Code does** ([MainMenu.swift:263, 314–339](../../Sources/BelloCodeApp/Shell/MainMenu.swift#L263)): **Push (`⌃⌘P`)** is in the **Changes** menu, not the **Git** menu (which has `Commit and Push…`, `Pull`, `Pull with Rebase`, `Fetch`, `Sync`, etc.).

4. **Secrets end-to-end smoke command fails as written ([README.md:128](../../README.md#L128)):**
   - **Doc says:** `BELLOCODE_SMOKE_SECRETS=1 build/BelloCode.app/Contents/MacOS/BelloCode --smoke-test`
   - **Code does** ([SmokeTest.swift:253](../../Sources/BelloCodeApp/Launch/SmokeTest.swift#L253), [SecretsEndToEnd.swift:11, 133](../../Sources/BelloCodeApp/Launch/SecretsEndToEnd.swift#L11)): Without `BELLOCODE_SMOKE_IMAGE`, `--smoke-test` defaults to `node:22-bookworm-slim`, which does not ship `curl`, causing `SecretsEndToEnd.run` (`curl -sS https://…`) to fail. (`docs/features/secrets.md:199` rightly passes `BELLOCODE_SMOKE_IMAGE=bellocode-secrets-test:1`, an image with `curl`.)

*(Note: `docs/USER-GUIDE.md:379–380` — telling users to click Stop in Settings ▸ Browser on `"Stop not confirmed"` — is tracked under `NV2-01` and will become accurate once `NV2-01` is fixed.)*
