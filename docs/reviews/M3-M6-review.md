# M3–M6 independent review

Reviewed `develop` statically on 2026-11-17. Verdict: **the execution and approval boundaries are not ready for enterprise use**. Counts: 3 critical, 6 major, 1 minor. These are code-derived scenarios, not reproduced incidents. No build, tests, app, container runtime, or live service was run. The earlier reviews and their dispositions were considered; settled findings are not repeated. Line references are repository-relative.

## Findings

### Critical

**C1 — Host Git executes repository-controlled programs.** `Sources/Engine/Git/GitRunner.swift:87` inherits the user's HOME, PATH and SSH agent, and :100–102 disables only hooks; `Sources/Engine/Git/GitRepository.swift:103` runs host `git status` and :230–232 runs host `git add`. A container command or an untrusted checkout with a writable `.git/config` can set `core.fsmonitor` to a script; the next automatic status executes it on the Mac. A configured clean filter plus `.gitattributes` executes on `git add`; `core.sshCommand`, credential helpers and remote helpers also run during host fetch/push (`Sources/Engine/Git/WorktreeService.swift:193` and `GitRepository.swift:252`). Disabling hooks does not disable these Git extension points or config includes. This works even if Rancher is unavailable, and exposes the host user and SSH agent. Move all repository Git operations, including opencode's own snapshots/worktree operations, into the container or enforce a complete, independently tested boundary that prevents Git from consuming attacker-controlled executable configuration. Test fsmonitor, filters, includes, SSH/credential helpers and worktree checkout, including after a container modifies `.git/config`.

**C2 — An agent can change an approved schedule without renewed consent.** `Sources/Engine/Extras/ExtrasHub.swift:216` lets any thread in the project edit any agent-created task (:240–244), including its prompt, destination and permission mode, while preserving approval; `Sources/Engine/Extras/SchedulerService.swift:139` persists the replacement. The approval card captures a snapshot of the original prompt (`ExtrasHub.swift:188–195`), but approval later applies to the current task by ID (:414–415). A prompt-injected agent can create an innocuous task, change it while the card is pending or after Allow Once, and have the altered prompt run persistently without the user approving it. Another project thread can do the same to an existing agent task. Bind approval to an immutable revision of the full task, invalidate it on meaningful changes, refresh the card, and enforce ownership or explicitly authorized project-wide mutation. Test both pending-card and post-approval edits and cross-thread attempts.

**C3 — Secret delivery lets the agent recover the secret despite its stated guarantee.** `Sources/Engine/Extras/ExtrasHub.swift:470–485` accepts a model-chosen shell command and passes the saved value in its environment. `Sources/Engine/Containers/EnvironmentService.swift:753–758` redacts only the exact plaintext from output. A malicious or injected agent requests a secret for a plausible reason, then runs `printf %s "$TOKEN" | base64`; the encoded value is returned to the model and stored in the tool result. It can also send it over the container's default outbound network or write it into the mounted repository. A competing same-user container process can inspect another process's environment while it runs; Docker exec configuration may also be inspectable by daemon clients, even though container configuration is clean. The host one-read FIFO similarly gives an agent-selected command access to the value (`Sources/Engine/Extras/SecretService.swift:72`), and command substitution can expose it in process arguments. A reference and exact-string redaction are not a confidentiality boundary against the recipient command. Replace the promise that the agent never sees the value with an enforceable narrow operation/credential broker and explicit user consent for the actual destination, or treat secret access as disclosure to the agent and communicate that accurately. Test encoded, split and network/file outputs, competing processes and exec inspection.

### Major

**M1 — GitLab tokens have no redirect or transport security boundary.** `Sources/Engine/Extras/Forge/GitLabProvider.swift:92–98` attaches `PRIVATE-TOKEN` to requests; `Sources/Engine/Extras/Forge/ForgeProvider.swift:80–96` uses a default URLSession with no redirect delegate to reject cross-origin or HTTPS-to-HTTP redirects. A reverse proxy or compromised configured server can redirect a request to another origin; the custom token header is not explicitly stripped, so its confidentiality depends on URLSession redirect behavior. `Sources/Engine/Extras/Forge/MergeRequestModel.swift:17` also accepts plain HTTP, exposing the token on the network by design. Reject redirects or validate every hop's scheme, host and port and explicitly remove credentials before any cross-origin request; require HTTPS except for an explicit enterprise-approved development policy. Verify with a real redirect receiver, including downgrade and nonstandard ports.

**M2 — Pagination can silently lose pages on revalidation and at the cap.** `Sources/Engine/Extras/Forge/GitLabProvider.swift:79–89` follows `X-Next-Page`, but the 304 branch at :103–105 restores only the body, not cached pagination headers (`ForgeProvider.swift:153–166`); if a 304 omits `X-Next-Page`, a second poll stops after page one. It also returns a partial result silently when the next page exceeds 10. A discussion on page two can disappear from the unresolved count, or a job can be missed, leading the watcher and user to believe review/CI is complete. Cache page metadata with the body or re-fetch when pagination metadata is missing; signal truncation rather than presenting partial results as complete. Add conditional multi-page and over-cap tests.

**M3 — Isolation verification reports success when nothing was verified.** `Sources/Engine/Containers/IsolationCheck.swift:55–68` treats skipped checks as non-problems and returns “Isolated”; :176–180 returns only a skipped server check when the server is unavailable. The nil-directory and blocked-runtime paths (:197–210) likewise permit a passing report without exercising execution. Moreover the configuration scan (:124–163) omits Git extension execution described in C1; a successful shell probe says nothing about it. A user can see a green isolation result while no command path ran, or while host Git remains exploitable. Introduce an explicit inconclusive state, require all applicable checks to run before a pass, and test actual independently enumerated execution paths. This is a diagnostic fix, not a substitute for enforcement.

**M4 — Forwarder connection bookkeeping races and can permanently exhaust admission.** `Sources/ContainerKit/Workspace/PortForwarder.swift:78–90` starts a task before inserting it into `tasks`. If a connection fails or completes immediately, it can remove its ID before insertion; the subsequent insertion retains a completed task forever. Repeating short connections eventually makes `activeConnections` hit 64 and all later browser requests are closed, even though none is active. Register before execution with synchronization or use an actor-owned slot whose completion cannot precede registration; add a deterministic immediate-completion test and verify stop closes active peers.

**M5 — Same-named projects share a writable worktree mount.** `Sources/Engine/Git/GitService.swift:39–42` derives the default worktree parent only from the project's last path component. `Sources/Engine/Containers/EnvironmentService.swift:791–805, 814–820` mounts that entire parent read-write in each project container. Opening `/team-a/service` and `/team-b/service` therefore gives both containers the same `~/.bellocode/worktrees/service` mount: a command in one can read or change the other project's worktrees. This happens without adding a user mount. Use a stable unique project identity for worktree parents, mount only authorized individual worktrees, and migrate or explicitly handle existing paths. Test same-name projects and worktree access from each container.

**M6 — Container exec output is silently truncated.** `Sources/ContainerKit/Workspace/ExecSession.swift:102–120` keeps only the last 1 MiB per stream without reporting overflow. `Sources/Engine/Containers/EnvironmentService.swift:768–773` further keeps only the last 8 KiB for setup; secret execution similarly returns a suffix (:756–758). A setup script can emit a failure or security warning early, followed by enough output to evict it, while its caller sees only the tail and a successful exit. This violates the visible-overflow rule and makes diagnosis misleading. Carry an explicit truncation flag/byte count through callers and UI, or spool with a bounded policy and report overflow; test sustained stdout and stderr separately.

### Minor

**m1 — Remote matching ignores the configured instance's port.** `Sources/Engine/Extras/Forge/MergeRequestModel.swift:85–115` matches only `host` for HTTP and SSH remotes. If two GitLab installations share a hostname on different ports, a remote on one port can resolve to the other instance and link or watch an unrelated project/MR. Match scheme and effective port for HTTP(S), and define a deliberate mapping for SSH ports and prefixed instances; test two same-host instances.

## Areas with useful safeguards

The helper uses argument arrays for Docker exec and refuses when its configuration, workspace or runtime is unavailable (`Sources/bellocode-exec/main.swift:45–55, 68–107`); that does not close C1. Default workspace containers drop capabilities, set no-new-privileges and do not mount the Docker socket; the forwarder binds IPv4 loopback (`Sources/ContainerKit/Workspace/WorkspaceSpec.swift:174`, `Sources/ContainerKit/Workspace/PortForwarder.swift:42–50`). The server constructs a separate environment and removes `BUN_*` (`Sources/OpenCodeKit/Server/ServerConfiguration.swift:84–113`), which addresses the stated environment-variable route to Bun; it does not prove every possible server/plugin launch path safe. Visuals use a nonpersistent store, a CSP and a content blocker, with host grants mediated by an app request (`Sources/BrowserKit/Visuals/HTMLVisualSandbox.swift:49–57, 94–107`; `Sources/Engine/Extras/ExtrasHub.swift:374–388`). Network grants authorize active content to communicate with the approved host, so they are a data-disclosure decision, not merely permission to load a library. These observations are limited to the inspected paths, not a security certification.

Design-system base controls expose an accessibility button role and press action, keyboard activation and focus state (`Sources/DesignSystem/Controls/DSControl.swift:74–80, 143–156, 182–219`). Static inspection cannot establish complete labels, focus visibility, contrast, text scaling or performance across their uses. Existing fixture and real-binary tests cover portions of these features, but do not establish the adversarial scenarios above; for example the GitLab fixture's 304 omits pagination headers (`Sources/Engine/Extras/Forge/ForgeProvider.swift:146–147`), and schedule approval tests (`Tests/EngineTests/ExtrasTests.swift:574`) do not demonstrate approval binding to a changed definition.

## Five fixes, in order

1. Remove host execution through Git and all other repository-controlled extension points (C1), and make isolation fail closed.
2. Bind schedule approvals to immutable task revisions and scope mutation authority (C2).
3. Redesign secret use around an enforceable, user-approved operation and destination; correct the confidentiality claim (C3).
4. Isolate and verify workspace mounts across projects (M5).
5. Make isolation results honestly inconclusive when coverage is missing, then secure GitLab transport and pagination (M3, M1, M2).

## Enterprise security decisions

Decide which container images, registries, outbound destinations and user-supplied mounts are permitted; whether agent-controlled code may ever receive a secret; what scope and duration of schedule/network grants are acceptable; and whether any HTTP GitLab endpoint is allowed. Decide whether the Rancher VM, local daemon users, host user processes and other containers are in the threat model. These policy choices do not remove the need for the code boundaries above.

## Human and live-service verification

Run the full `docs/research/03-ux-patterns.md` section E checklist with mouse, keyboard and VoiceOver, including Increase Contrast, Reduce Transparency, large text, focus, performance and multiple windows. Verify actual macOS/Rancher mount and symlink semantics, isolation probes, runtime failure and process cleanup on a disposable machine, with explicit security approval. With a real self-managed GitLab and registry, verify TLS, redirects, prefixed paths, authentication, pagination/304, rate limits, wake-once behavior and credential visibility. Check sandboxed visuals and browser behavior against hostile pages at the screen. None of those checks, tests, or the feature notes' benchmark claims were independently verified in this review.
