#### NF03 (Incomplete — `major`)
- **Location:** `Sources/BelloCodeApp/Shell/WorkspaceController.swift:138-155`, `Sources/BelloCodeApp/Content/ThreadContainerViewController.swift:73-95`
- **Failure scenario:** On cold launch restoring a thread before `ProjectModel` finishes seeding (or when opening a child/notification/deep-linked thread whose session is not yet in `openThreads` or `row(id)`), `makeSurfaceContext(for: .thread(id))` computes `directory = ""` and `makeContext` skips `projectShown` (`if !context.directory.isEmpty`). - **Fix:** Observe `context.directory` (or `thread.session?.directory`) and invoke `projectShown(directory)` as soon as a non-empty directory becomes known. Add a regression test exercising late session hydration and asserting `engine.environments.projectsInUse` contains the project directory.

  2. At launch (`Engine.swift:340-356`), `core.loadCache()` loads Thread A directly into `pipeline.state.sessions` without emitting `.lineage` events; then `sharedBrowser.start()` calls `followThreadEnds()` with an empty `ThreadEndTracker(archived: [:])`; then `core.start()` reconciles from opencode, where `ProjectionState.putSession` (`ProjectionState.swift:178`) skips unchanged sessions (`guard sessions[session.id] != session else { return }`).

### Major Findings

#### NV01 — `Git ▸ Move Changes to New Worktree…` dumps the user onto a dead "No Thread Selected" screen
- **Severity:** `major`
- **Location:**
  - `Sources/BelloCodeApp/Shell/MainWindowController+Git.swift:371-374`
  - `Sources/BelloCodeApp/Shell/WorkspaceController.swift:156-157, 176, 252-258`
  - `Sources/BelloCodeApp/Content/ThreadContainerViewController.swift:92-95, 104-117`
- **Problem:** `presentHandoff()` moves uncommitted changes into a newly created worktree (`created.directory`, e.g. `~/BelloCode/Worktrees/repo/<branch>`) and calls `workspace.newThread(in: created.directory)` (`MainWindowController+Git.swift:374`). That selects `.draft(directory: created.directory)`. However, `WorkspaceController.makeSurfaceContext(for: .draft(directory:))` (`WorkspaceController.swift:156-157`) guards on `projectItem(directory: directory)` (`engine.root.projects.first { $0.directory == directory }`). Because a worktree is not registered in `engine.root.projects`, `makeContext` returns `nil` and `ThreadContainerViewController.display` renders the empty `"No Thread Selected"` placeholder instead of a composer.
- **Failure scenario:** User makes uncommitted edits in a local checkout and invokes **Git ▸ Move Changes to New Worktree…**. Handoff succeeds, shows the notice `"Moved changes to <branch>"`, and immediately replaces the workspace with `"No Thread Selected"` (no composer, selection stuck on an unshowable draft for the worktree path).
- **Suggested fix:** Either open a draft in `project` pre-selecting the existing worktree `created.directory` in `WorkspaceDraft`, or create a thread directly in `created.directory` (`engine.createThread(in: created.directory)`) and select `.thread(id)`. Add a shell integration test exercising `presentHandoff` through selection display.

#### NV02 — `GitLab ▸ Show Merge Requests` (`⌃⌘M`), `Show Issues` (`⌃⌘I`), and `Show To-dos` (`⌃⌘Y`) are disabled on new-thread drafts and empty state, with a false Command Palette reason
- **Severity:** `major`
- **Location:**
  - `Sources/BelloCodeApp/Shell/ShellCommand.swift:778, 810, 881`
  - `Sources/BelloCodeApp/Shell/MainWindowController+Agents.swift:28-35`
  - `Sources/BelloCodeApp/Content/MergeRequestSurface.swift:160-165`
- **Problem:** `CommandContext.isEnabled` gates `.showMergeRequests` on `agents.available` (`ShellCommand.swift:778`) and `.showIssues` / `.showTodos` on `gitLab.configured && agents.available` (`:810`). `agents.available` (`MainWindowController+Agents.swift:29`) is `true` only when `agents?.model?.threadID != nil` (an existing thread is displayed). Yet `MergeRequestPanelModel` explicitly supports `.issues` on new-thread drafts (the exact workflow fixed in NF09 and NF18) and `.todos` across all configured GitLab instances with no thread open. Furthermore, `disabledReason(for:)` (`ShellCommand.swift:881`) unconditionally returns `"Connect GitLab in Settings ▸ GitLab"` for `.showIssues` and `.showTodos` even when `gitLab.configured == true`.
- **Failure scenario:** With GitLab configured, the user presses `⌘N` to start a new thread (or has no thread selected) and invokes **GitLab ▸ Show Issues** (`⌃⌘I`), **GitLab ▸ Show To-dos** (`⌃⌘Y`), or **GitLab ▸ Show Merge Requests** (`⌃⌘M`). All three are greyed out and their shortcuts beep/do nothing. Opening `⌘K` and typing `issues` or `to-dos` shows them disabled with `"Connect GitLab in Settings ▸ GitLab"` despite GitLab being connected.
- **Suggested fix:** Enable `.showMergeRequests` whenever `gitLab.configured || agents.available` (or `container.context != nil`), `.showIssues` whenever `gitLab.configured && container.context != nil` (thread or draft), and `.showTodos` whenever `gitLab.configured`. Update `disabledReason` to distinguish `!gitLab.configured` from missing project/context.

#### NV03 — `ComposerTextView.performKeyEquivalent` swallows `⌃⌘↩` (`Git ▸ Run Suggested Git Action`) and `⌃⌥⌘↩` (`GitLab ▸ Submit Review…`) as newlines
- **Severity:** `major`
- **Location:**
  - `Sources/ComposerKit/View/ComposerTextView.swift:64-73`
  - `Sources/ComposerKit/Model/SendKeyPolicy.swift:66-78`
  - `Sources/ComposerKit/View/ComposerViewController.swift:995-1009`
  - `Sources/BelloCodeApp/Shell/ShellCommand.swift:572, 591`
- **Problem:** `ComposerTextView.performKeyEquivalent(with:)` (`ComposerTextView.swift:65`) matches *any* Return/Enter keyDown where `event.modifierFlags.contains(.command)`, without excluding `.control` or `.shift`. For `⌃⌘↩` and `⌃⌥⌘↩`, `SendKeyPolicy.action` (`SendKeyPolicy.swift:66-78`) falls through to `.newline`, and `ComposerViewController.composerTextView(_:handleReturn:)` (`ComposerViewController.swift:1001-1008`) inserts a newline and returns `true`, consuming the event before AppKit routes it to the menu bar.
- **Failure scenario:** While focus is in the composer (the user's primary focus location), pressing `⌃⌘↩` (**Git ▸ Run Suggested Git Action**) or `⌃⌥⌘↩` (**GitLab ▸ Review ▸ Submit Review…**) never triggers the menu command and instead inserts a blank line into the draft prompt. Violates `AGENTS.md` UX rule 2.
- **Suggested fix:** In `ComposerTextView.performKeyEquivalent(with:)`, only claim Return combinations that `SendKeyPolicy.action` maps to `.send` (or reject events carrying `.control` / `.shift`), returning `false` so `⌃⌘↩` and `⌃⌥⌘↩` pass through to the menu bar. Add a regression test in `ComposerKitTests` verifying `performKeyEquivalent` returns `false` for `⌃⌘↩` and `⌃⌥⌘↩`.

#### NV04 — `Window ▸ opencode…` and `Window ▸ Project Environment…` pass a worktree path instead of the project root, breaking Settings pickers and reading/writing opencode trust under the wrong directory
- **Severity:** `major`
- **Location:**
  - `Sources/BelloCodeApp/Shell/MainWindowController.swift:203-205`
  - `Sources/BelloCodeApp/Launch/AppDelegate.swift:255-259, 326-332`
  - `Sources/BelloCodeApp/Settings/OpenCodeSettings.swift:185-199, 223-228, 390-398`
  - `Sources/BelloCodeApp/Settings/ContainerSettings.swift:707-708, 949-960`
  - `Sources/Engine/OpenCodeConfig/OpenCodeConfigService.swift:146, 164-175`
- **Problem:** `MainWindowController.currentProjectDirectory` (`MainWindowController.swift:203-205`) returns `context.directory.isEmpty ? context.projectDirectory : context.directory`. For any thread running in a git worktree (`context.directory` = worktree path, `context.projectDirectory` = registered project root), it returns the **worktree** path. Both `AppDelegate.showOpenCodeSettings(_:)` (`:255-259`) and `AppDelegate.showEnvironment(_:)` (`:326-332`) feed that path directly into Settings panes whose project pickers (`model.projects`) only contain `engine.root.projects` root directories.
- **Failure scenario:** While viewing a worktree thread (project `/src/app`, worktree `/Worktrees/app/feat-x`):
  1. Choosing **Window ▸ opencode…** sets `OpenCodeSettingsModel.selectedProject` to `/Worktrees/app/feat-x` (missing from the Project dropdown). `OpenCodeConfigService.isTrusted` (`:146`) checks exact key equality (`trusted[directory] != nil`), so even when `/src/app` is already trusted, the switch falsely shows **Off**. Toggling it **On** writes trust only for `/Worktrees/app/feat-x` (a temporary worktree), leaving `/src/app` and its other worktrees untrusted.
  2. Choosing **Window ▸ Project Environment…** sets `EnvironmentSettingsModel.directory` to `/Worktrees/app/feat-x`, mismatching the Project picker and displaying the worktree leaf name (`feat-x`) and path; if the worktree is not yet in `workspaceRoots`, `EnvironmentService.environment(for:)` creates an orphan `ProjectEnvironment` keyed by the worktree.

#### NV07 — `EgressProxy` leaks in-memory `SecretUseLedger` reservations on `useRecorder` failure or placeholder Upgrade refusal, and leaves durable counts incremented on P5 `reauthorize` refusal
- **Severity:** `minor`
- **Location:**
  - `Sources/SecretKit/EgressProxy.swift:621-639, 666-676`
  - `Sources/Engine/Secrets/SecretManager.swift:929-946`
- **Problem:**
  1. At `EgressProxy.swift:621-624`, `ledger.reserve(made, limit: limit)` increments the in-memory ledger before `await recorder(made)` persists to SQLite. If `recorder(made)` returns `false`, `guard allowed else` refuses the request without calling `ledger.release(made)`, permanently leaking the reserved count in memory.
  2. At `EgressProxy.swift:635-639`, if `wantsUpgrade && !uses.isEmpty`, the request is refused with 403 without calling `ledger.release(uses)`.
  3. In P5's AF15 `reauthorize` check (`:666-676`), if a policy change/revocation causes `reauthorize` to fail after `recorder(made)` already persisted `secret.uses[binding]` to SQLite (`:623`), `ledger.release(uses)` decrements memory only, leaving the refused request permanently counted in SQLite across relaunch.
- **Failure scenario:** On a `maxUses = 1` secret binding, a transient SQLite failure in `recordUses` or an attempted WebSocket Upgrade permanently exhausts the in-memory budget until app restart; a revoked request refused by `reauthorize` permanently consumes a durable use on next launch.
- **Suggested fix:** Call `ledger.release(made)` if `recorder(made)` returns `false` or if `wantsUpgrade` refuses the request; check `wantsUpgrade` before reserving uses; optionally persist durable uses only after `reauthorize` (or accept fail-closed over-counting explicitly).
