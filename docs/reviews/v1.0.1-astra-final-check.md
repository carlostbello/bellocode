## AF01 · blocker · Generating a commit message can disclose a file outside the checkout

**Problem.** When the index is empty, commit-message generation reads each untracked path through Foundation. That read follows a symlink. Git stages the link target’s name, while the model prompt receives up to 2,000 bytes of the target’s contents. The 64 KiB check also happens after the read.

**Failure scenario.** A local setup tool creates an untracked link to a small private configuration file outside the checkout. The developer selects Generate Message. The private text goes to the configured model before the developer can review the proposed message.

**Suggested fix.** Read project files relative to the worktree directory descriptor, represent a symlink by its link text, and bound reads of regular files before allocating. Verify the generated prompt using an outside marker.

## AF02 · blocker · The CLI password and server endpoint come from different authorities

**Problem.** The authenticated broker supplies the server PID and password. The wrapper obtains the URL from a separate owner-writable discovery file. It checks for a live PID and a loopback host, but never binds that port to the server that issued the password.

**Failure scenario.** If the discovery URL is changed by same-account host-file access while the genuine server is running, a subsequent ordinary CLI call can present the genuine server-wide password to a different loopback listener. The file’s private permissions and the broker’s executable check both succeed in this case.

**Suggested fix.** Return the verified endpoint, server identity and credential in one authenticated broker response. Use that endpoint for the invocation. Treat the file as a discovery hint and reject discrepancies.

## AF03 · blocker · Use accounting can make revocation disappear after relaunch

**Problem.** Revocation saves a whole secret row and updates the in-memory record after the await. A completing use also saves a whole row, using the current in-memory policy. SQLite serializes both writes but has no policy revision check.

**Failure scenario.** An in-flight broker request completes while revocation is waiting on storage. Its count update captures the old active policy and is written last. Settings can show Revoked for the rest of this launch. On reopening, the broker accepts the active row again without a placeholder grant.

**Suggested fix.** Store monotonic use counters independently, or merge counter updates into the durable row in one transaction. Fence policy mutations per account. Gate a final count write against revocation and check the row through a fresh store reader.

## AF04 · blocker · A thread’s old placeholder grant can deliver a replacement value in clear text

**Problem.** Saving an existing label from a request card can change its mode and value without retiring earlier grants. Environment delivery checks the secret’s current mode, scope and confirmation. It does not check the grant kind that the particular thread received. The existing `grantFits` method already distinguishes the two kinds at load time.

**Failure scenario.** Thread A has only a placeholder. In thread B in the same project, the owner saves a replacement under the same label and confirms Visible. A reconnect during the same app launch rebuilds A’s environment from its old grant and injects the new value. A never received a visible grant.

**Suggested fix.** Invalidate incompatible grants on every mode-changing save, including replacement from a request card. Require `grantFits` at environment delivery and when reusing an existing grant. Check both threads after a reconnect.

## AF05 · blocker · Restore Stashed Changes discards the staged version of a file

**Problem.** The worktree handoff now restores the index. The separate branch-switch action still calls `applyStash` with its default `index: false`, removes the parked entry, then drops the stash after a successful apply.

**Failure scenario.** A file has one committed version, a second version staged, and further unstaged edits. After Stash and Switch, switching back and selecting Restore Stashed Changes restores the working file and discards the normal recovery handle for the staged-only content. The current parked-stash test edits only the working file.

**Suggested fix.** Restore the saved index as well as the working files in this action. Keep the stash parked until both have been verified, and cover the three-version case through the branch-switch UI model.

## AF06 · blocker · A pending Git push can publish to a different repository from the one approved

**Problem.** The approval card includes the resolved push URL. Execution checks the local branch and HEAD, then asks Git to push to the mutable remote name. The destination in the approval is never enforced.

**Failure scenario.** While a push card is pending, another Git client repoints the remote to a different writable GitLab project. With the same local HEAD and a destination branch that accepts the push, approving the original card sends the commits to the second project.

**Suggested fix.** Bind the operation to the approved, resolved destination and local object ID through execution, including credential selection. Invalidate the card if that mapping changes. Verify using two distinct repositories on the same instance.

## AF07 · blocker · Dev-container staging can copy a host directory outside the project

**Problem.** The copier queues directory pathnames and resolves each again when enumerating its children. The final identity check covers the context root. The clone and copy flags protect only the final path component.

**Failure scenario.** If a nested directory becomes a symlink while the context is being staged, a regular file below the new target can be copied into the private context. The root retains its original identity and the copy is handed to the builder. This requires a concurrent change within the project.

**Suggested fix.** Open each source directory relative to a verified parent with no symlink following. Enumerate and copy from those pinned descriptors, enforce bounds on the opened objects, and refuse a changed directory identity.

## AF08 · blocker · Repository instruction reads can cross the project boundary during directory replacement

**Problem.** The v1.0.1 loader correctly rejects a pre-existing link that resolves outside the repository. It then opens the checked absolute pathname in a separate operation. Its no-follow flag covers the leaf, and the descriptor check establishes only that the opened object is a regular file.

**Failure scenario.** A prompt-time scan overlaps a replacement of an ancestor of a previously resolved instruction file. The resulting descriptor can refer to external text, which the plugin then installs as session instructions. This requires concurrent access to the checkout and applies in the default untrusted-project mode.

**Suggested fix.** Anchor the open to a pinned repository root, walk ancestors without following links, and verify the opened object’s confinement before reading bytes. Cover ancestor replacement as well as a static external symlink.

## AF09 · major · Workspace provisioning runs project-image programs as root

**Problem.** Even with a valid numeric non-root workspace user, home preparation executes the project image’s `/bin/sh` and utilities as `0:0`. The workspace’s project and cache mounts are already attached, and the container has ownership and discretionary-access capabilities.

**Failure scenario.** A project-built image with a customized shell or ownership utility runs that implementation during workspace initialization. It can change files and ownership on writable mounts with the privileges reserved for BelloCode’s setup step. The privilege here is container root.

**Suggested fix.** Initialize home and cache volumes in a trusted helper with only those volumes mounted. Run the project image with its final non-root UID and remove the setup capabilities from the workspace.

## AF10 · major · A named workspace user is verified after image code starts

**Problem.** The create path starts the image’s `sleep` executable under the configured name, then trusts the output of the image’s own `id` program. Reuse and concurrent-create adoption also return container IDs without requiring a successful UID check.

## AF11 · major · CRLF Dockerfiles can pass the registry allowlist without checking a base image

**Problem.** The directive and instruction readers split Swift `Character` values on LF. CRLF forms one extended grapheme cluster. A CRLF file that starts with an ordinary comment can therefore be consumed as a single comment and return an empty image list.

**Failure scenario.** A Windows-edited Dockerfile has a leading comment and a base image outside the configured registries. BelloCode approves the empty list. Docker recognizes the following instruction and can pull the unapproved image during either supported build path.

**Suggested fix.** Normalize physical line endings once at the byte level and share the result across both parser passes. Exercise a commented CRLF Dockerfile against both registry policy entry points.

## AF13 · major · An oversized HTTP chunk declaration can crash the Docker filter’s host process

**Problem.** The chunk reader accepts an arbitrary nonnegative `Int` size and adds framing bytes using checked Swift arithmetic. Its body limit is applied only after the addition and a subsequent read.

**Failure scenario.** A malformed chunk-length declaration from an authenticated workspace client fits in `Int`, but adding the framing length overflows. The host app traps while reading the declaration, before the normal oversized-body error can be returned.

## AF24 · major · An external editor’s config save can be silently overwritten by Settings

**Problem.** BelloCode serializes its own edits and detects an external change made before its final comparison. The comparison and atomic replacement are separate operations. The post-write check reads only the selected model key.

**Failure scenario.** An editor saves an unrelated setting after the comparison and before BelloCode’s rename. Settings then installs its older full document, verifies the intended model key and reports success. The unrelated edit is lost.

**Suggested fix.** Use a replacement operation that preserves the displaced file until its contents can be checked, or coordinate writes with participating editors and preserve a recoverable conflict copy for other writers. Exercise the interval between comparison and replacement.

## AF25 · major · A nonregular Dockerfile can stall dev-container preparation before its timeout

**Problem.** Verification opens the resolved Dockerfile for a blocking read and only then uses `fstat` to require a regular file. A FIFO with no writer blocks in `open`, before the validator or the Docker child deadline can return an error.

**Failure scenario.** An opted-in project points to a leftover named pipe as its Dockerfile. Checking the context or starting the build can remain pending indefinitely. Cancelling the Swift task does not interrupt that blocking system call.

**Suggested fix.** Open nonblocking and without following links, require a regular file on the opened descriptor, then perform the bounded read. Report the invalid input during both tag calculation and staging.

## AF26 · major · Failed cleanup of a visible session environment is never retried after the last grant is removed

**Problem.** Revocation removes the grant and attempts to replace the session’s command environment. An unavailable client or failed environment request is swallowed. Reconnection rebuilds environments only for sessions that still have grants.

**Failure scenario.** The server remains alive across a temporary client disconnect when the owner revokes a thread’s only visible secret. If the cleanup request never reaches the server, new commands in that thread continue receiving the old value after reconnection. Revocation can already have been reported as complete.

**Suggested fix.** Track sessions awaiting environment cleanup independently of their remaining grants. Keep failed revocations visibly pending for those sessions until the replacement is acknowledged. Cover a transient disconnect with the same server process.

## AF27 · minor · A preference-read error can overwrite the delegated-model mirror and clear its own warning

**Problem.** On startup, a failed preference read sets `storageProblem` but still marks the plugin mirror stale. A successful mirror write publishes the in-memory fallback choice and clears the read error.

**Failure scenario.** A transient store failure occurs while a previously saved delegated model and its mirror are valid. The plugin switches to the thread model, and Settings no longer shows why. A later successful load can restore the saved choice.

**Suggested fix.** Keep a confirmed mirror on read failure, preserve the read error, and retry the preference read before updating the plugin. Handle an absent preference separately from an unreadable one.
